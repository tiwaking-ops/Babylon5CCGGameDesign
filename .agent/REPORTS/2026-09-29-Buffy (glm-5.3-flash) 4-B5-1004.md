# B5-1004 — Offer distribution across claiming lanes (DONE)

## Reproduction (the row's first requirement)

Synthetic TEMP fixture (`$TEMP/b5-1004-fixture`: 20-OPEN-row ledger, script
copy, empty CLAIMS/HEARTBEATS — never the live ledger): the pre-fix runner
offered **the identical head row on all 20 iterations** (`B5-7001` ×20),
matching the seed pass's live observation of 10 lanes all offered B5-1000.

## Diagnosis

The main loop took `$free[0]` every iteration, and DryRun `continue`s without
claiming — so concurrently launched lanes, all starting at iteration 1 on the
same census, converged on the head. The atomic claim file was the only
serializer: a correctness backstop doing a scheduler's job.

## Fix (offer-selection only; two anchored regions)

`Select-OfferRow` + `Test-OfferMarkerAvailable`: for each candidate row a lane
tries an **OS-atomic exclusive CREATE** of a per-row marker under %TEMP%
(keyed per ledger), holding the owning lane's PID. First lane to touch a row
wins; the loser walks to the next candidate. No read-modify-write step exists,
so there is no race window — the filesystem separates the lanes, not a lock
protocol. A marker blocks only while its owner is alive (dead owners'
markers reclaimed; unreadable → 2-minute age bound; infrastructure failure →
fail-open), so finished runs never suppress later ones. The in-run hashtable
prevents a lane re-offering its own rows; `$PID` anchors the start offset.

## Design evolution — the receipts drove it

| Design | Concurrent-lane receipt | Disposition |
|---|---|---|
| v1: stateless `$PID % N` | 2 of 3 distinct (Windows PIDs are mostly multiples of 4 → offset collisions) | discarded |
| v2: mutex + JSON read-modify-write | 3/3, then 2/3 (lost-update window; a lock-timeout path degraded to stateless selection) | discarded |
| v3: atomic-create per-row markers, PID-liveness bound | **3 of 3 distinct, three rounds running** | kept |

The v2→v3 rewrite exists because v2's failure mode was the exact one the row
warned about in reverse: a TTL-era intermediate offered **zero** rows on the
1-lane control (suppress-forever markers), which fails the negative control
even while "passing" a distinctness count.

## Receipts (final design, all on the fixture)

- **R1 in-run distinctness**: 20 of 20 offers distinct across 20 iterations
  (`all distinct offered: 20`).
- **R2 one-lane negative control**: exactly **1** offer.
- **R3 concurrency**: 3 concurrent lanes → **3 of 3 distinct first offers**,
  in each of three consecutive rounds.
- **Live tree**: DryRun `-MaxIterations 3` offered three distinct rows in one
  run (B5-1022, B5-1023, B5-1024).
