## Flag schema recommendation: SUBTYPE-STRUCTURED (not boolean)

Recommend keeping contingency identity as the card **type** with structured keys,
exactly the loader contract above — not a boolean flag:

1. The engine keys host legality on `canTarget` via `validTargetType`/`validTargetRace`;
   a boolean would force a parallel schema the loader already ignores.
2. The SNRPG source distinguishes contingencies by type with per-card trigger variety;
   a boolean collapses information the source data has.
3. Precedent contrast: B5-0386 recommended a boolean for *mercenary* because that
   mechanic had no structural hook in the model. Contingency is the opposite case —
   fully structured (host + trigger + effect id) — so the structured form is correct.

Future Great War import template (zero new keys, loader defaults make partial records
safe): `"type":"CONTINGENCY", "subtype":"CHARACTER", "validTargetType":"CHARACTER",
"triggerCondition":"WHEN_ATTACKED"` (+ an event-registry effect id if a scripted effect
is wanted) — byte-for-byte the shape the HCT:2580-2587 parse fixture already verifies.

## Reusable lesson

Absence verdicts should cross-check the SNRPG decode tables before closing: a card type
can be real in the source universe (Great War) yet correctly absent from a premiere +
deluxe pool — absence from data is not absence from design, and the engine may already
be waiting for the data (B5-0365 precedent) or vice versa (mercenary's engine-first path).
