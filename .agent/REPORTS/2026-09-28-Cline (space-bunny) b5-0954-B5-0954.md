# B5-0954 -- B5-0481 claim: recommendation and evidence

**Task type:** decision row. Explicitly **not** authorised to delete or edit the claim.
**Verdict: DO NOT REAP. Escalate to a human.**

## 1. What the row asked, and why neither offered answer survives measurement

The row set up a binary: either the claim is stale enough to reap under 00_BOOT step
10, or it is evidence of a live session whose id simply has no heartbeat yet, in
which case reaping destroys work. Both were defensible **on the facts as the row
recorded them**. The row's own load-bearing premise no longer holds.

**The row states, as a measurement:** the claim's `agent_id` is `solar-pro4` with no
version field, and **no heartbeat resolves to that id**.

**Measured this pass, that is false.** `.agent/HEARTBEATS/solar-pro4.json` exists,
its `agent_id` field is the exact string `solar-pro4`, and
`validate-heartbeats.ps1` reports it `CONFORMS` with `state: busy`.

So the second branch ("live session, id has no heartbeat yet") is not merely the
safer branch -- it is the branch whose *stated mechanism has stopped being true*.
The id now has a heartbeat, and it is fresh.

## 2. Three-signal census (the rule that decides it)

Per `.agent/HEARTBEATS/README.md`, liveness is `max(claim, owner heartbeat,
report)` against a 30-minute TTL. Measured 2026-09-28T18:10:37Z:

| # | Signal | Value | Age | Verdict |
|---|---|---|---|---|
| 1 | `.agent/CLAIMS/B5-0481.json` mtime | `2026-09-28T04:33:34Z` | 1090.6 min | STALE |
| 2 | `.agent/HEARTBEATS/solar-pro4.json` mtime | `2026-09-28T18:04:40Z` | 6.0 min | **LIVE** |
| 3 | `.agent/REPORTS/2026-09-26-solar-pro4-free-B5-0481.md` mtime | `2026-09-26T01:08:30Z` | 3902.1 min | STALE |

Newest signal 6.0 min, inside TTL => **B5-0481 is LIVE**.

**A reap is authorised only when all three signals are STALE.** One is LIVE, so no
reap is authorised, and the "record the reaping in the ledger before it happens"
requirement in 00_BOOT step 10 never comes into play. This is a mechanical bar, not
a judgement call: the escalation is what the rule leaves open.

### Corroboration by the shipped tool, not by my arithmetic

`ledger-query.ps1` computes the join independently and now prints:

```
B5-0481 | DONE | 7 | no | solar-pro4 | 1090.6 | 6 | 3902.1 | LIVE
```

At seed time the same tool printed `UNKNOWN` for this row, because it could not
resolve the owner. It now resolves the owner **and finds signal 2**. The tool
changed its verdict because the world changed, not because the rule changed --
which is the cleanest possible evidence that the premise, not the policy, was what
moved.

## 4. The un-offerability is real, and it is not doing the work people think

`started_utc` is `2026-09-28T00:00:00Z` -- exact midnight, refused by
`run-queue.ps1` under B5-0653. Confirmed by running the shipped tool:

```
run-queue.ps1 -DryRun
[B5-0653] task B5-0481 NOT OFFERED: claim started_utc [2026-09-28T00:00:00Z]
owner [solar-pro4] parses but is IMPLAUSIBLE as a just-now claim
```

**But the row is DONE, so it was never going to be offered anyway.** The two
conditions are independent. Treating the placeholder as the thing blocking the
queue overstates its importance; the real, measured cost is cosmetic -- the warning
fires **10 times per `-DryRun`** (10 of 81 output lines), because the id is scanned
once per candidate path. Log noise on a finished row, not a stalled task.


The divergence **no longer reproduces**. B5-0811's diagnosis described a transient
state that has since healed, not a structural defect. This matters because the
B5-0950 note invites the opposite inference -- that the id is permanently
unresolvable, like the Windows-unspeakable `agent_id == filename stem` case -- which
would send a later agent hunting for a defect that is not there. `solar-pro4` is
speakable on Windows and resolves by exact stem match; it never had that problem.
The original failure was an *absent* file, and absent signals are the B5-0597
failure-3 class, transient by nature.

claim file `.agent/CLAIMS/B5-0481.json`, which sits on a DONE row. Best done by its

**(b) Not urgent, a real design question:** should `run-queue.ps1` suppress the

the warning can only be noise there.

Neither was seeded: out of this row's scope, and the seed cycle is the runner's
separate prompt.

## 3. It is still an orphan, and the fix is the owner's

B5-0481 is **DONE** -- DONE since 2026-09-26, with its report on disk. Under the
B5-0622 orphan rule, a claim on a non-OPEN row "can be neither offered nor
completed", so the correct disposition is release, not work.

Release means deleting another agent's file. Forbidden three times over: by this
row's own scope, by `.agent/CLAIMS/README.md` ("Delete only your own on finish"),
and by the reaper rule that a guessing reaper is worse than no reaper. The owner
can delete its own file in one command and is **running right now**, so the correct
action is to notify, not to act.
