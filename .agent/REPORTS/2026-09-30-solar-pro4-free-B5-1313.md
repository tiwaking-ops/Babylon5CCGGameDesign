### Cost notions on the live tree

**1. RulesEngine.sponsorCost (lines 242-247) — the correct notion for characters.**
Composes:
- `baseRecruitCost(p, ch)` (line 246): `card.getCost()` doubled if `ch.getFaction() != p.getFaction()` (other-race loyal doubling, rulebook §Sponsor), plus `1 per existing IC member` (B5-0321 seam — `innerCircle.size()`, since the ambassador is seated in IC).
- Then `sponsorDiscount` grant/consume (B5-0339): assistant rotates for -1 sponsor cost later that turn; consumed by the first recruit.
- Then `FREE_SPONSOR` waiver: if `CardEffects.sponsorWaiver(ch) == FREE_SPONSOR`, the entire cost is waived (line 243-244).
- Result: `SponsorCost(getAmount(), discountApplied, waived)`.

**2. RulesEngine.canRecruit (line 252-254) — the real recruit gate.**
Line 254: `return p.getAppliedPool() >= sponsorCost(p, ch).getAmount();`
Both the gate AND the charge (GameController line 231: `int cost = sponsorCost(p, ch).getAmount()`) read the SAME notion — `sponsorCost`. The RECRUIT_CHARACTER path is internally consistent: affordability-gated, cost-charged from the same value, double-cost and sponsor-discount both sit inside the gate.

Verification (B5-1109 scratch probe, 9/9 pass by reflection): RECRUIT on a MINBARI cost-3 character at pool 6 charges doubled 6 and seats the card; at pool 2 it is refused with the card staying in hand.

**3. GameController.applyGenericCardPlay (lines 630-684) — CHARGES card.getCost RAW.**
Line 636: `int cost = card.getCost();`
Line 637: `if (cost > 0 && !p.applyInfluence(cost)) { ... return; }` — charges raw, no doubling, no discount, no waiver.
The method ALSO has a sponsor-agenda check at line 646 (`canSponsorAgenda`) but that is for AgendaCard only, not CharacterCard.

For a CharacterCard dispatched to `applyGenericCardPlay`:
- It IS NOT an Enhancement/Location/Group/Agenda/Event/Contingency.
- It falls through all `instanceof` branches.
- It is removed from hand (line 651) and logged (line 652).
- It receives NO effect (no supporting-role placement, no IC seat, no sponsor discount consumption).

This is the corruption B5-1109 named: dispatching `playCard` on a CHARACTER charges raw cost (e.g. 3) instead of sponsor cost (e.g. 6 if other-race loyal), removes it from hand, and discards it to the deck with no effect. The character is LOST — not recruited, not placed, just gone.

### canPlayCard's price is wrong in the DISCOUNT direction
B5-1109 found: with a sponsor discount of 2, a pool of 2 is REFUSED by `canPlayCard` while `canRecruit` ALLOWS it at a true charge of 1. This is because `canPlayCard` reads `card.getCost()` (raw 3) minus nothing — it does not know about the assistant sponsor discount. `canRecruit` reads `sponsorCost.getAmount()` (1 after discount). The discrepancy is harmless only because nothing calls `canPlayCard` on the recruit path.

### The genuinely reachable defect: applyGenericCardPlay + CharacterCard
B5-1109 identified the real defect one level over: `applyGenericCardPlay` (line 630) charges `card.getCost()` raw and falls through to deck discard for any card that is not Enhancement/Location/Group/Agenda/Event. If a CharacterCard ever reaches `applyGenericCardPlay` via `PLAY_CARD`, it is charged raw, removed from hand, and discarded — no recruitment, no IC seat, no sponsor discount consumed.

This is the defect B5-1313 logs the interpretation for, and it is the defect B5-1341 (the path census) confirms is currently UNREACHABLE from all paths (AI, UI, harness), and B5-1321 (the fix) is scoped to route CHARACTER through the sponsor gate.

## The exact condition under which canPlayCard becomes load-bearing

`canPlayCard` becomes load-bearing on the CHARACTER path if and only if a production caller dispatches a CharacterCard to `applyGenericCardPlay` (or any path that consults `canPlayCard` before playing a card). As of B5-1109's close-out, NO production caller does this:
- AIPlayer.buildLegalActions routes CharacterCard to `recruitCharacter`, never `playCard` (AIPlayer.java line 191 — `else if (c instanceof CharacterCard)` branch).
- MainWindow.playOnly refuses `selectedCard instanceof CharacterCard` (MainWindow.java line 2147-2148).
- MainWindow.updatePlayInitiateButtons (line 2134) calls `rules.canPlayCard(humanPlayer(), selectedCard)` as a production enablement check — this line landed with B5-1177 AFTER B5-1109 closed. It does NOT open a CharacterCard path (line 2130 excludes it), but it IS a production caller of `canPlayCard` that B5-1109's "zero production callers in MainWindow" claim did not capture. The count is now 1, not 0. The claim is time-stamped: accurate when written, stale after B5-1177.

So `canPlayCard` is currently load-bearing on ZERO character dispatches. It becomes load-bearing the moment any of these changes:
1. AIPlayer offers `playCard` for a CharacterCard (would need an explicit code change — currently excluded by the `else if (c instanceof CharacterCard)` branch at line 191 of AIPlayer.java).
2. MainWindow.playOnly removes or bypasses the `instanceof CharacterCard` guard (line 2147-2148 of MainWindow.java).
3. Any new action type or dispatch path routes a CharacterCard to `applyGenericCardPlay` without going through `canRecruit`.

### What the first production caller must be checked against
When the first production caller of `canPlayCard` on a character dispatch appears, it must be checked against `RulesEngine.sponsorCost` — NOT `card.getCost`. The discrepancy B5-1109 found (canPlayCard refuses at pool 2 when canRecruit allows at charge 1, because canPlayCard does not know about the assistant sponsor discount) means `canPlayCard` on a character path would:
- Refuse playable recruits (false negative) when a sponsor discount makes the true charge lower than raw cost.
- Allow unplayable recruits (false positive) when the other-race doubling makes the true charge higher than raw cost — but this case is already gated by `canRecruit` on the recruit path, so the danger is specifically on NON-recruit character paths (i.e., `applyGenericCardPlay` routing).

The check: any new production caller of `canPlayCard` for a card that could be a CharacterCard must either (a) route through `sponsorCost` instead, or (b) be paired with a gate that checks `canRecruit` (which already reads `sponsorCost`). The B5-1109 finding that `canPlayCard`'s price is wrong in the DISCOUNT direction means a standalone `canPlayCard` check on a character is NOT a substitute for `canRecruit` — it would be stricter in the wrong direction.
