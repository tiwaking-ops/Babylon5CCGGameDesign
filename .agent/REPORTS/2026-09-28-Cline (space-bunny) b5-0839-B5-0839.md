# B5-0839 — the "166 .md files missing author_llm" finding, measured

**Row:** B5-0839. **Result:** DONE. **No `.md` file was edited, no provenance was
added or repaired, no `b5ccg/src` was touched, no commit.** One report, one pattern,
one DECISIONS entry, this row. The measurement harness lives outside the repo tree
(`%TEMP%\b5-0839\`), so not even a scratch file was added to the repository.

## The controls, first, before the number

The row's premise is that a single number is uninterpretable. It was. Both controls
ran before any triage, using a harness that reimplements the detector's block
**verbatim** from `.agent/tools/verify_task.py` lines 189-194, so the numbers are
comparable rather than re-derived by a second opinion.

| Control | File | bare token | detector regex | Expected |
|---|---|---|---|---|
| positive x3 | `AGENTS.md` | True | **True** | has provenance |
| positive x3 | `.agent/00_BOOT.md` | True | **True** | has provenance |
| positive x3 | `.agent/AGENT_LOOP.md` | True | **True** | has provenance |
| negative | scratch file in `%TEMP%`, never in the repo | False | **False** | missing |

**CONTROL VERDICT: positive=True, negative=True -> the detector is DISTINGUISHING.**

This is the outcome the row was built to force, and it is the one that made the rest
of the work possible: a positive-only control suite would have "passed" a detector
that flags everything, and the failure mode B5-0831 recorded — a control that can
never fail — would have repeated with the sign flipped. The negative control is a
file this session created, so its "no provenance" status is a fact rather than a
memory.

## The headline number is inflated 1.68x by a glob bug

| Quantity | Value |
|---|---|
| `.md` files enumerated by the detector | **1264** |
| `missing_provenance` as reported | **168** (row said 166; it drifts — the count is live, and my own report adds to it) |
| **Distinct** files behind that count | **100** |
| Duplicate enumerations | **68** |

The cause is in the detector's own three-line enumeration, which is not disjoint:

```python
md_files  = [p for p in ROOT.glob("docs/**/*.md")        if p.is_file()]
md_files += [p for p in ROOT.glob(".agent/**/*.md")      if p.is_file()]
md_files += [p for p in ROOT.glob(".agent/REPORTS/*.md") if p.is_file()]
```

`.agent/REPORTS/*.md` is a **subset** of `.agent/**/*.md` (pathlib's `**` matches zero
or more directories), so line 3 re-adds every REPORTS file line 2 already collected.
`missing_provenance` is built by iterating that list, so each REPORTS file is counted
twice. The namespace breakdown makes it arithmetic rather than inference: REPORTS
reads **68 distinct** and **136 enumerated** — exactly double — while PATTERNS (30)
and docs/proposals (2), neither of which is in line 3's glob, read the same either way.
`68 + 30 + 2 = 100`.

**So the number is wrong before the question of whether the underlying finding is real
is even asked.** Any future report quoting "N md files missing provenance" is quoting a
count of *enumerations*, not of files.

## The split: 39 real, 61 detector false positives

Of the 100 distinct files, classified by an independent method that does not reuse the
detector's regex (it asks what `author_llm` line is actually present):

| Class | Count | Real gap? |
|---|---|---|
| `author_llm` **BARE SCALAR** — `author_llm: Buffy (glm-5.3-flash)` | 45 | **No — false positive** |
| `author_llm` **absent entirely** (no token in the file) | 39 | **Yes** |
| `author_llm` present but not at line start (prose/backtick mention) | 14 | **Yes** (no field) |
| `author_llm:` flow-map with `name:` but **no** `version:` | 2 | **Partial** — §1 requires both |
| token present, no `author_llm:` field at all | 1 | **Yes** |
| `author_llm` as a list item / sub-key, not a top field | 1 | **Yes** |

**39 real · 61 false positive (45 of which are the single bare-scalar class).**

### Why the bare-scalar class is a false positive, and it is the interesting finding

`AGENTS.md` §1 states the requirement in prose, in this exact form:

> Every LLM-created `.md` MUST open with `author_llm: <name> (<version>)`

The detector's regex requires instead a **YAML flow-map with two quoted literals**:

```python
r"author_llm:\s*\{[^}]*name:\s*\"[^\"]+\".*?version:\s*\"[^\"]+\"[^}]*\}"
```

Those are two different specifications. A file whose frontmatter reads:

```yaml
author_llm: Buffy (glm-5.3-flash)
```

**satisfies the written governance requirement exactly** and is flagged as missing,
because the regex only recognises the alternative form the rulebook's own frontmatter
happens to use. Verified directly: that file's `last_modified_by_llm: {name: "Buffy",
version: "glm-5.3-flash"}` line sits two keys below it, is fully compliant, and is
adjacent to the "missing" field without rescuing it.

This is the B5-0831 lesson landing in a new place: **the gate can be the thing that is
wrong, and here it is wrong in the direction that manufactures a governance crisis out
of a documentation-format mismatch.** 45 of 61 false positives are this one cause.

## Asymmetry check: the detector is not biased toward "missing"

A detector that flags everything and a detector that flags nothing both yield a large
plausible number, so the controls were complemented by a leakage check:

| Quantity (distinct) | Value |
|---|---|
| enumerated `.md` containing the token `author_llm` | 725 |
| enumerated `.md` with **no** `author_llm` substring at all | **39** |
| reported missing (distinct) | 100 = 39 token-absent + 61 token-present-but-rejected |
| token-absent but **not** reported missing | **0** (must be 0) |

`0` leaks. The detector reports **every** file that genuinely lacks the token, and adds
61 files that have it in some form. So the error is **one-directional and
over-inclusive**: it never misses a real gap. That is the *safe* direction for a
governance check — it is why this finding is a false alarm rather than a missed
violation — and it is worth stating explicitly, because a detector that both over- and
under-reports could not be repaired by simply reading its output more carefully.

## What this row does not claim

* **It does not repair the detector.** `.agent/tools/verify_task.py` is under **live
  claim B5-0833** (`solar-pro4:free`, started 07:39:45Z) and is outside this row's
  scope, which is `report only plus read-only tree walks`. The two detector defects —
  the overlapping glob inflating the count 1.68x, and the regex contradicting
  AGENTS.md §1 — are reported here for whoever holds that scope, and **not fixed**.
* **It does not add provenance to any of the 39 files**, for the §1 reason above.
* **It does not claim the 61 are "fine".** The 45 bare-scalar files comply with §1 *as
  written*; the 14 prose-mention files and 1 list-item file have the token but no
  usable field; the 2 partial files name an author without a version. These are
  separate, smaller questions, each needing its own decision.
* **The count is live and drifts.** My own report and pattern add two more files on
  this very pass, and both are compliant, so the distinct count rises while the
  real-gap count does not. A future re-measurement should expect a different number and
  should not read the difference as a regression.

## Reusable lesson

**Build the negative control before you read the number, and check whether the rule and
the checker are even the same rule — 45 of 61 "missing" files satisfied the governance
clause verbatim, because the detector enforced a YAML shape the clause never asked for;
a gate that contradicts its own spec manufactures a crisis, and the tell is a finding
that concentrates entirely in the namespace where nobody is looking.**
