# B5-0919 — HeadlessConformanceTest.java: size and structure

**Scope honoured: measurement only.** No source file was edited, no check was
moved, the check count is unchanged, nothing was refactored, nothing was
committed. The only files written are this report, one pattern, the ledger row,
`docs/DECISIONS.md`, and my own heartbeat. Every number below was measured from
the file as committed, not estimated.

**Gate: GREEN.** `b5ccg\compile.bat` exits 0 on JDK `1.8.0_292` with
`-source 6 -target 6`. The suite itself also runs green:
`java -cp out b5ccg.engine.HeadlessConformanceTest` → exit 0,
`CONFORMANCE SUITE PASSED (643 checks)`.

## 1. The size premise, confirmed

`b5ccg/src/b5ccg/engine/HeadlessConformanceTest.java` is **5961 lines**, the
largest source file in the tree, and the gap is not marginal:

| Rank | File | Lines | Multiple of the runner-up |
|---|---|---|---|
| 1 | `HeadlessConformanceTest.java` | **5961** | — |
| 2 | `ui/MainWindow.java` | 2326 | 2.56x |
| 3 | `engine/RulesEngine.java` | 1447 | 4.12x |
| 4 | `ai/AIPlayer.java` | 1233 | 4.84x |
| 5 | `engine/GameController.java` | 813 | 7.33x |

Line composition: **4306 code / 1057 comment / 598 blank**. The file is
dominated by real code, not by a comment banner, so the size is not a
documentation artifact that a shorter header would fix. Max brace nesting is
**5** (line 4481) — deep but not pathological, so the file reads as a long
sequence of shallow, independent tests rather than one deeply nested routine.

## 2. Structure: 58 live sections, and yes, one flat `main`

**There is exactly one `main` (line 5853, the last 108 lines of the file).** It
is a **flat sequential call list**: 58 calls to 58 `test*` methods, guarded by a
single `try`/`catch (Throwable)`, with no dispatch, no reflection over section
names, no table, and no per-section error isolation. One failing section aborts
every section after it and is reported as `unexpected exception` rather than as a
named failed check. So "643 checks run as one flat sequence in a single main" is
**confirmed literally**, and it is also a real robustness property worth naming.

Sections are delimited by `// ── <name> ─────` banner comments: **122 banner
lines**, but only **58** of them open a called test section (the rest are
in-method sub-banners, e.g. the `// --- Path 1: ... victory ---` markers inside
`testVictoryPathQuery`). **The section names are method names**, not banner text
— the banners are decorative and drift-prone, and a reader must read the method
declarations to learn the real section list.

**Check invocations.** There are **654 `check(` call sites** and 1 `skip(` site
(residual). Runtime reports **643**. The three numbers reconcile exactly, and
the reconciliation is the most useful finding in this report:

```
  654  check( call sites in the file
 -  1  the check() declaration itself (line 105)
 - 18  inside testCostField, which is never called from anywhere  (dead code)
 ----
  635  reachable call sites
 +  8  net extra executions from checks inside loops (85 sites live inside
       a for/while; the loops run more than once)
 ----
  643  runtime checks
```

**`testCostField()` (line 3921, 94 lines, 18 checks) is dead code.** It is the
only one of 59 defined `test*` methods never invoked from `main`, and the string
`testCostField(` appears exactly once in the whole tree — its own declaration. So
**18 assertions of card-cost behaviour are silently not running**, and the file's
own Javadoc advertises the coverage (`CST Card cost field: cards carry an
influence cost...`). This is a coverage hole, not a size problem, and it is
**reported here, not fixed** — fixing it is a source edit, which this row
forbids. It should be its own task.

The largest resulting class is **#3 at ~1424 lines**, which is under the current
`RulesEngine` (1447) and far under `MainWindow` (2326) — the split removes the
outlier without creating a new one. **Dependency order is strictly one-way and
layered**: `Support` <- `Conformance*` sections <- `Runner`. `Support` imports
only `model`/`model.enums`/`ai` and no section class; section classes import
`Support` and the engine; `Runner` imports all six section classes and is the
only class that knows the order. That ordering makes the split mechanically
checkable — a cycle is impossible unless a section imports another.

**Cost in runner wiring — this is not free, and the row asked for honesty about
it.** The blast radius is smaller than it looks but is not zero:

1. **`b5ccg/compile.sh:52` invokes the class by name, at exactly one line:**
   `java -cp "$OUT" b5ccg.engine.HeadlessConformanceTest`. A split keeps this
   line valid **only if** the runner class keeps the name
   `b5ccg.engine.HeadlessConformanceTest` — i.e. the name must stay on the
   orchestrator, not move to a section. That is one constraint on where the
   split boundary falls, and it is why the table above puts `main` in its own
   `Runner` role *without* renaming it. **Net: 0 lines changed in `compile.sh`.**
2. `compile.sh:53` also runs `HeadlessSmokeTest`, and `compile.bat` runs **no**
   suite at all (it only compiles; verification is `RUN_TESTS=1` in the `.sh`).
   So the Windows gate is compile-only and a split cannot break it.
3. **Three other files name `HeadlessConformanceTest` — all in comments only**
   (`HeadlessParticipationGatesProbe:24`, `HeadlessReportingTiebreakTest:234,247`,
   `HeadlessWarConflictProbe:17,282`, all of the form "mirrors
   HeadlessConformanceTest"). There is **no code-level coupling**, so no import
   or call site outside the file needs touching.
4. `checks` / `failed` are **private static** fields of the single class (lines
   102-103) and are the suite's only cross-section state. They must move into
   `Support` and become package-visible, or the split silently resets counters
   and turns a red suite green. **This is the one genuinely risky step** and the
   reason a split needs a verification step, not just a compile.
5. **The exit contract must be preserved exactly**: `System.exit(failed == 0 ?
   0 : 1)`, and the two `System.out.println` summary lines, because
   `compile.sh:52-54` has no parsing — it relies on the JVM exit code alone.

**Verification a split would have to pass (so it is not presented as free):**
compile green on JDK 8 `-source 6`; runtime `CONFORMANCE SUITE PASSED (643
checks)` — the literal number, since a counter bug shows up as a changed total
before it shows up as a wrong assertion; and the negative control that
`testCostField` is still not called, so the count stays 643 and not 661.

**Recommendation:** the split is *sound and low-blast-radius* (0 lines of build
wiring change), but it is **not urgent relative to its cost**, because the file's
real defect is the 18 dead checks in `testCostField`, not its length. Fix that
first as a small, separately-claimed task. The split is worth doing when someone
is already editing the AI or conflict areas, and the mechanical guard on the
counter migration is the thing to write down when it is done.

## 4. Honest limitations

* The `654 -> 643` reconciliation attributes the 8-check surplus to loop
  multiplicity. I verified there are no commented-out `check(` sites, none in
  helpers, and none directly inside `if`/`while`/`for` headers; the surplus is
  consistent with the 85 in-loop sites executing more than once. A per-section
  instrumented run would pin the exact attribution, and I did not instrument
  the file, because that is an edit.
* The group boundaries in section 3 are a *proposal* built from rule area, not
  from recorded intent in the file. Group 6 in particular is the weakest grouping
  and would want a maintainer's judgement.
* No timing, no per-section runtime, and no coverage-tool run: those need
  instrumentation or an external agent, none of which is in scope here.

## Reusable lesson

When a file's headline number disagrees with its own instrumented number, the gap
is the finding: here `654` call-sites against `643` runtime checks located an
entire 18-check dead test method that the file's own Javadoc advertised as
covered. The count of assertions in a file is not the count of assertions that
run, and only running it tells you which.
