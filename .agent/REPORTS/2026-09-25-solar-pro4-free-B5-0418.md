# B5-0418 — Contingency-card identification research

*`author_llm: Solar Pro4 (solar-pro4:free)`*

## What

Searched both card pools (premiere.json 446 cards, deluxe.json 383 cards = 829 total) and the SNRPG corpus for contingency, reveal, placed-under-host, and trigger-hook language. Delivered a no-evidence verdict plus a flag schema.

## Method

- **Pool scan**: loaded both `b5ccg/out/cards/*.json` files (the compiled-copy copies that `DeckLoader.loadBothSets()` actually hydrates), scanned every card's `text` + `flavorText` fields for placement verbs (play on / placed under / attach to / under a host), reveal language (reveal / turn face up / face up / flip), and any contingency-keyword occurrences. Also enumerated every `type` and `subtype` value in both pools to check for a CONTINGENCY card type or contingency-flavored subtype.
- **SNRPG corpus**: surfaced the canonical wikipedia/wikibin Babylon 5 CCG rules article (the surviving SNRPG rulebook reference) and the CardGuide wiki. The rules text confirms the contingency mechanic exists in the tabletop game: played face-down on a card already in play, remains hidden until its trigger is met, reveals optionally, one per action round unless stated otherwise. None of this mechanic appears in the project's card data.
- **Engine cross-check**: confirmed `DeckLoader.java:283` has a `case CONTINGENCY:` branch that hydrates `ContingencyCard` objects from `validTargetType`, `validTargetRace`, and `triggerCondition` JSON keys; `Card.java:33/150` carries the `contingency` sub-list API (`getContingencies()`, `addContingency`, `removeContingency`); `RulesEngine.java:663/682` has `canPlayContingency`/`canRevealContingency`; `CardEffects.java:193` has `revealContingency`. The engine plumbing is fully implemented (B5-0365 territory) — it is the data that is absent.

## Findings

### F1 — No evidence of contingency cards in either pool (VERDICT: NO-EVIDENCE)

| Pool | Cards | Type=CONTINGENCY count | Contingency-keyword text matches |
|------|-------|------------------------|----------------------------------|
| premiere.json | 446 | 0 | 0 |
| deluxe.json | 383 | 0 | 0 |
| **Total** | **829** | **0** | **0** |

- No card in either pool has `type == "CONTINGENCY"`; no card has a contingency-flavored `subtype`.
- No card text contains placement language specific to contingency (play face-down on an existing card, placed under a host, reveal when trigger met). The "attach to" language belongs to Enhancements (which attach to Characters/Fleets/Locations, not to other cards as hidden triggers); the "reveal" language belongs to Events/Groups/Characters (force opponent to reveal, or reveal own hand) — none of it is a hidden trigger-reveal loop.
- The SNRPG rules article confirms the contingency mechanic exists in the tabletop game, so the absence is a data gap, not a misunderstanding of what to look for.

### F2 — Engine is ready; data is the blocker

The engine already supports the full contingency lifecycle:
- `DeckLoader.java:283` — `case CONTINGENCY:` hydrates `ContingencyCard` from JSON keys `validTargetType`, `validTargetRace`, `triggerCondition`.
- `Card.java:33/150` — host card carries a `List<ContingencyCard>` with add/remove/get APIs.
- `RulesEngine.java:663` — `canPlayContingency(Player, ContingencyCard, Card host)`.
- `RulesEngine.java:682` — `canRevealContingency(Player, ContingencyCard)`.
- `CardEffects.java:193` — `revealContingency(GameState, Player, ContingencyCard)`.
- `GameController.java:186-195` — PLAY_CONTINGENCY branch; `GameController.java:201-204` — reveal branch.

The engine can load and execute contingency cards today if the data exists. The blocker is purely data: no card JSON row has `type: "CONTINGENCY"`.

### F3 — Flag schema recommendation

For any future contingency data work, use a **subtype-based flag** rather than a boolean, because the tabletop contingency space is heterogeneous (different triggers, different host restrictions, different reveal obligations). Proposed schema:

| Flag | Type | Values | Notes |
|------|------|--------|-------|
| `isContingency` | boolean | `true` | Required; routes DeckLoader to `case CONTINGENCY:` at `DeckLoader.java:283`. |
| `triggerCondition` | string enum | `ANY`, `WON`, `LOST`, `WON_MILITARY`, `LOST_MILITARY`, `WON_DIPLOMACY`, `LOST_DIPLOMACY`, `WON_INTRIGUE`, `LOST_INTRIGUE`, `WON_PARTICIPANT`, `LOST_PARTICIPANT`, `MILITARY_PARTICIPANT`, `DIPLOMACY_PARTICIPANT`, `INTRIGUE_PARTICIPANT`, `PSI_PARTICIPANT`, `WON_DIPLOMACY`, … (match the AftermathCard trigger enum already in the codebase) | Required; drives the reveal condition. The existing AftermathCard trigger vocabulary at `DeckLoader.java:280` is reusable here. |
| `validTargetType` | string enum | `CHARACTER`, `FLEET`, `LOCATION`, `GROUP`, `ANY` | Required; the host card type the contingency can be placed under. Mirrors `DeckLoader.java:284`. |
| `validTargetRace` | string enum | faction names + `ANY` | Optional; restricts host race. Mirrors `DeckLoader.java:285`. |
| `revealOptional` | boolean | `true`/`false` | Optional; SNRPG says reveal is optional. Defaults to `true` if absent. |
| `limitPerRound` | integer | 1 (default) | Optional; SNRPG says one contingency per action round unless stated otherwise. |

Boolean-only schema (`isContingency: true/false`) is insufficient because the trigger condition and host restrictions are the operationally meaningful fields — a boolean flags the row but the enum fields drive the rules engine behavior.

## Verdict

**No-evidence verdict.** Neither card pool contains a single contingency card. The engine is fully wired (B5-0365). A future data task (B5-0424, gated on this verdict) would need either (a) human direction on which contingency cards to source from SNRPG, or (b) a design decision to skip the contingency data entirely. Either way this task's deliverable is the no-evidence verdict plus the flag schema above — no card list is possible because there are zero card candidates.

## Reusable lesson

A "search for X in the data" task that returns zero hits should still confirm the engine/model actually supports X (here: `DeckLoader.case CONTINGENCY` + `Card.contingency` sub-list + `RulesEngine.canPlayContingency`/`canRevealContingency` + `CardEffects.revealContingency`) and deliver the schema for how X would be represented — that way the downstream backfill task (B5-0424) has a ready-made flag spec instead of re-deriving it. The SNRPG rules corpus is a legitimate secondary source for verifying what the mechanic is, but the in-tree engine code is the authoritative source for what the project actually implements.
