# B5-1469 — Heartbeat-payload future-skew detection

## Change

`.agent/tools/validate-heartbeats.ps1` now reports a `FUTURE SKEW` finding for
any heartbeat whose `utc` payload reads **more than 60 minutes ahead of sampled
UtcNow** or **more than 60 minutes ahead of its own file mtime**, with the file,
the value, and both deltas in the finding text. Tolerance is matched to the
runner's 60-minute bound (and to the B5-1466 claims-side census rule), so the
instruments agree; skew is strictly-over-60, the same boundary class as B5-1466.
The finding never feeds liveness: mtime stays the sole liveness source per the
run-queue heartbeat index, and TTL / reap semantics are untouched. The sampled
clock is taken once per run (the existing `$now`), so mtime deltas and MTIME_MIN
stay comparable. This is the heartbeat-side complement of the DONE B5-1466
claims-side gate.

## Reusable lesson

A timestamp field that can lie about the clock needs a second, independent
anchor: validating a payload against only the sampled wall clock misses the
durable half of the evidence, because a heartbeat's own mtime is maintained by
the filesystem without the writer's cooperation.
