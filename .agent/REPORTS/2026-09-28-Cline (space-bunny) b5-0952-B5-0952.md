# B5-0952 — future-dated claim guard, DONE

Agent: `Cline (space-bunny) b5-0952` (client Cline, model space-bunny; the `b5-0952`
discriminator is mine and no other session is using it). Claim held on
`.agent/CLAIMS/B5-0952.json` for the duration and deleted at close-out. Scope claimed:
`.agent/run-queue.ps1` plus one DECISIONS entry, this report, one pattern, heartbeat.

## The defect

B5-0653 made the runner refuse a claim whose `started_utc` is exactly midnight UTC or at
or before the Unix epoch. That is a guard against the **past**. Nothing guarded the
**future**, and a future-dated claim is not merely un-refused — it is actively wrong:

```
(now - started)  ->  negative
negative  <  ttl  ->  always true  ->  verdict LIVE
```

A negative age compares as younger than any TTL. This is the *same inversion* as the
B5-0597 failure-3 defect, where a join matching no heartbeat file returned `-1` and `-1`
compared as younger than the TTL, rendering four claims LIVE with zero verification. The
consequence is not a fast-failing row but a row that **cannot age out**: it reads LIVE
until the wall clock catches up, which for a 12-hour offset is half a day of an
un-offered task.

Measured at seed time: claim `B5-0939` carried `started_utc 2026-09-28T22:05:00Z`
against a wall clock of `2026-09-28T10:14Z`, and `ledger-query.ps1` printed its age as
**MINUS 711.7 minutes** while still rendering the verdict LIVE.

### Decisions worth defending

**Tolerance = 60 minutes, not 14.** The row asked for a tolerance "generous enough to
absorb clock skew and timezone mistakes". I did not go to 14 hours, and deliberately so:
a 12-hour offset is *precisely the failure being fixed*, so a tolerance wide enough to
absorb every real timezone would not be a fix. The reasoning that does hold is
narrower — the claim is written and read **on the same host**, so the only skew worth
absorbing is write-to-read drift plus a NTP resync landing between them, and Windows
w32time resyncs on a ~1024 s (17 min) interval within a ±15 min band. 60 min covers a
full resync cycle with margin. A larger offset (a +5:30 or +13 zone, a hardcoded
"tomorrow") is a data-entry defect, not drift, and is refused loudly.

**Direction rule preserved, not re-derived.** From B5-0653: ambiguity resolves toward
NOT OFFERING. The two error classes are not symmetric — a wrongly-refused live claim
costs one blocked task the owner clears in seconds by re-claiming, a wrongly-accepted
future-dated claim costs a collision and destroyed work.

**One-sided by construction.** A past-dated claim is left entirely to B5-0653. Two
guards that each own one direction beat one guard that owns both, because the second
one has to reason about the past-tense cases it was never written to test.

**Non-repair preserved.** A claim file belongs to its owner. The guard warns, never
edits — same as B5-0653.

**`Get-CensusSuppression` deliberately NOT changed**, and it now carries a comment
recording why. That function also branches on `$started -gt $now`, and it looked like
the same bug in a second place. It is not: suppression is the *fail-safe* direction
there — it makes a row NOT reportable, silencing a possible defect report rather than
manufacturing one. Suppressing-while-refusing agree on the outcome "not offered" by
different routes, so that line needs no bound of its own. Left alone, with the reason
written down, because a future reader finding a `> $now` branch in a file they just
fixed deserves to know it was considered.

## Two things I got wrong on the way, recorded because both were invisible without them

**A failing assertion is only evidence once you know which side is wrong.** The first
harness run reported 1 of 8 failing: the "no claim file" case was not offered. My first
instinct was that the new guard was over-blocking. It was not — the fixture was writing
a claim file with no `started_utc` for that case, which is legitimately LIVE via file
mtime. The guard was right and my test was wrong. Had I "fixed" the guard to satisfy
that assertion, I would have shipped a regression to make a broken test pass.

**`git diff --stat` lied about the size of my change.** It reported 255 insertions on a
file where I had written roughly 120 lines. The surplus was the B5-0900 seed branch —
another agent's uncommitted work already in the working tree. Worth stating plainly: an
uncommitted dirty tree means a diff is not attributable to you by default, and a
reviewer reading the stat alone would have credited me with (or blamed me for) another
agent's feature.

## State note

The live `B5-0939` claim had already been re-written with a real timestamp
(`2026-09-28T17:48:39Z`) by its owner before this pass reached it, so the live tree no
longer exhibits the defect. The fix is **preventive** against the class, and the row's
own evidence for the class (a second instance, a future-dated `utc` on
`me-so-poor.json` from B5-0949) is on a file outside my scope, which I did not touch.

**Reusable lesson:** a timestamp guard that only rejects the past is half a guard — and
the missing half is the dangerous one, because a negative age satisfies every "is it
fresh" comparison and never ages out. When you add a bound in one direction, check
what the arithmetic does in the other.
