## Incident recorded: stale `.git/index.lock`

The first staging attempt failed: `.git/index.lock` existed, timestamped
19:04:35 local (06:04:35Z). Diagnosis before removal: the only running git
processes were short-lived **opencode snapshot** commands whose command lines
name a *different* `--git-dir` (a snapshot store under the user profile), so
none could hold our index lock; the lock's age (4+ hours) matched the
B5-0647 checkpoint session of solar-pro4:free, whose commit (`1a54145b`) had
landed and whose session had since died and even returned under a different
claim. Conclusion: a stale sentinel from a dead process, removed, and the
removal documented here per the reap-evidence discipline — a lock file is
coordination state, and deleting one is only safe when the owner's death is
established, not assumed.

## Reusable lesson

A stale lock is diagnosed, not guessed: match its timestamp against the
process table (including *which git-dir* each live process addresses) and the
session history before removing it — and record the removal like any other
reap, because it is one.
