# B5-0641 — Victory-path surfacing audit (report-only)

## Audit scope

Read-only audit of `b5ccg/src/b5ccg/ui/` (MainWindow.java, GameBoardPanel.java) plus the
engine victory-check path in `b5ccg/src/b5ccg/engine/RulesEngine.java` (checkVictory and its
private helpers) and `b5ccg/src/b5ccg/model/AgendaCard.java` (isConditionMet). No source edits.

Grounded observation from the task row: RulesEngine.checkVictory at line 559 returns a Player
only with no path output, and MainWindow.java:1432 shows the winner name only, so a 10-point
Major win or a met-agenda win reads identically to a Standard win.

## The five victory paths in the engine

checkVictory (RulesEngine.java:559) implements five distinct paths, tested in order:

| # | Path | RulesEngine line(s) | Rulebook | What qualifies |
|---|------|---------------------|----------|----------------|
| 1 | Last standing | 560-567 | :170 last-standing | only one non-forfeited player remains |
| 2 | Station condition 2 | 580-581, stationVictory 625-641 | :176 condition 2 | Babylon 5 influence >= 20 AND exactly one non-forfeited, non-major-agenda player strictly leads in Power; Shadow War inert |
| 3 | Agenda condition | 591-593 | :170/:174 agenda win condition | player's revealed agenda.isConditionMet(state, p) returns true (INFLUENCE_20, MILITARY_SUPREMACY, MOST_INNER_CIRCLE, or unknown key falling through to influence >= 20) |
| 4 | Major Victory path 1 | 602, majorVictory 671-677 | :182 | player has >= 20 Power AND >= 10 more than every other non-forfeited player |
| 5 | Standard Victory | 607, standardVictory 654-658 | :170/:176 condition 1 | player has >= 20 Power AND strictly more than every other non-forfeited player (no major agenda in play; Shadow War blocked since B5-0629) |

Note: path 4 (Major Victory) and path 5 (Standard) can both be satisfied by the same player in
the same state — Major fires first because of ordering at line 602 vs 607. A player with 30 Power
and everyone else at 15 qualifies for both; the engine returns Major. A player with 25 Power and
everyone else at 20 qualifies for Standard only (Major requires a 10-point gap; 25-20=5 fails).

Note: path 3 (agenda condition) fires before path 4 and 5. A player whose MILITARY_SUPREMACY
agenda is met at 15 Power wins via path 3 even though they would not qualify for Standard (below
20) or Major (below 20).

## What the UI currently surfaces

### MainWindow.java:1431-1436 — the only game-over surfacing

```java
if (state.isGameOver()) {
    statusLabel.setText("GAME OVER — Winner: "
        + (state.getWinner() != null ? state.getWinner().getName() : "None"));
    passButton.setEnabled(false);
    playCardOnlyButton.setEnabled(false);
    initiateConflictButton.setEnabled(false);
}
```

This is the ONLY place that surfaces game-end victory information to the player. It shows:
- "GAME OVER" label
- "Winner: <player name>" (or "None" if winner is null, which should not happen when isGameOver
  is true since isGameOver returns winner != null per GameState.java:352)
- button disablement

It does NOT show:
- which victory path fired
- the Power/Influence totals that triggered the win
- the agenda type or win condition key if path 3 fired
- whether the station reached 20 influence if path 2 fired
- whether the winner had a 10-point lead (Major) or a strict-lead-only (Standard)
- the last-standing count if path 1 fired

### GameBoardPanel.java:186-192 — conflict outcome banner (NOT game victory)

This surfaces conflict resolution outcomes ("WON BY <name>", support/opposition totals,
influence reward) but it is per-conflict, not per-game. It is irrelevant to the game-ending
victory-path question except that a player might confuse a conflict win with a game win.

### No other victory surfacing found

Grep across ui/ for "victory", "Winner", "GAME OVER", "gameOver", "isGameOver", "getWinner",
"checkVictory" returns only the MainWindow game-over block and the GameBoardPanel conflict
outcome block. No agenda-condition readout, no Power-total readout at game end, no path label.

## Gap analysis by path

### Gap 1 — All five paths render identically (P0/HIGH)

**File/line:** MainWindow.java:1432

**Observation:** Regardless of which of the five paths fired, the player sees exactly:
"GAME OVER — Winner: <name>"

A player who wins via MILITARY_SUPREMACY agenda at 15 Power sees the same message as a player
who wins via Standard Victory at 25 Power with a strict lead, who sees the same as a player who
wins via Major Victory at 30 Power with a 10-point lead, who sees the same as a player who wins
via station condition 2 (station at 20+ influence), who sees the same as the last player standing
after everyone else forfeited.

**Severity:** P0/HIGH — the player cannot tell why they won. For a solo playtest or AI-run game
watched via the log, this is a curiosity gap. For a human playing the UI, this is a "what did I
just achieve?" gap with no answer in the interface. The rulebook draws a meaningful distinction
between these paths (:170 vs :176 vs :182) and the player deserves to see which one they scored.

**Note:** The engine log DOES emit "WINNER: <name>" at GameState.java:353 via setWinner, but that
is a raw log line, not a structured victory-path signal, and the UI does not read the log for this.

### Gap 2 — Agenda win condition key is not surfaced (P1/MEDIUM)

**File/line:** MainWindow.java:1432 (no agenda readout); AgendaCard.java:22-48 (isConditionMet
has the key but never exposes it to the UI)

**Observation:** When path 3 fires, the player wins because their agenda's win condition was met.
The agenda has a winConditionKey (INFLUENCE_20, MILITARY_SUPREMACY, MOST_INNER_CIRCLE, or other).
The UI shows only the winner name. The player does not see which agenda condition they satisfied.

**Severity:** P1/MEDIUM — a player holding a MILITARY_SUPREMACY agenda who wins by crushing
everyone's fleets deserves to see "won by Military Supremacy" rather than a bare name. This also
applies to MOST_INNER_CIRCLE (a political dominance statement) and INFLUENCE_20 (the most common
agenda condition, often met alongside Standard but distinguishable when the player is below 20
Power and wins via agenda alone).

**Dependency:** Surfaceing the agenda win condition requires the agenda card (or its win condition
key) to be available at the game-over surface. The winner Player has getAgenda() (model), but
MainWindow's game-over block does not consult it.

### Gap 3 — Power total at victory is not surfaced (P2/LOW)

**File/line:** MainWindow.java:1432 (no Power readout)

**Observation:** The engine knows the winner's Power (Player.getInfluence()) and the field values
that triggered the win (station influence for path 2, Power gap for paths 4 and 5, fleet totals
for MILITARY_SUPREMACY agenda). None of these are shown.

**Severity:** P2/LOW — a Power total readout at game end is a nice-to-have that lets the player
see how close the win was (a 20-19 Standard win vs a 35-10 Standard win tell very different stories).
Not required for correctness; the path label in Gap 1 is more important.

## Proposed slice

**One slice only (per task constraint):** Add a victory-path label to the MainWindow game-over
status line, reading the path from a new enum returned by checkVictory.

**What the UI would show (proposed):**

```
GAME OVER — Winner: <name>
<path label>
```

Where path label is one of:
- "Last standing — all others forfeited"
- "Station condition 2 — Babylon 5 influence >= 20"
- "Agenda victory — <agenda win condition key>"
- "Major Victory — 20+ Power and 10+ point lead"
- "Standard Victory — 20+ Power and strict lead"

**Does this need an engine path API first?** YES.

checkVictory currently returns `Player` only (RulesEngine.java:559). The five paths are
distinguished inside private helper methods (stationVictory, agenda.isConditionMet, majorVictory,
standardVictory) and the last-standing check, but the caller (GameController.java:136-138) and
the downstream consumer (MainWindow via state.getWinner()) receive no path information.

To surface the path in the UI without the UI reaching into engine internals, the engine must
expose the path. The minimal API shape is one of:

(a) Change checkVictory's return type to a small value object carrying both Player and a
    VictoryPath enum — this is a model/engine change, not a ui/ change, and it touches the
    GameController call site at line 136-138.

(b) Add a separate getVictoryPath(GameState) query that the UI can call alongside getWinner() —
    this keeps checkVictory's signature but adds a second engine entry point the UI consumes.

Either way, this is an engine API change (model/ or engine/) that the ui/ read-only task B5-0641
cannot itself implement. The ui/ slice proposed here (reading the path enum from state and rendering
it in the status line) is a downstream ui/ task that depends on the engine API landing first.

**Recommendation:** File the engine API task (enum + return-type or query) as a follow-up, then
file the ui/ rendering slice as a second follow-up that claims after the engine task is DONE.

---

Reusable lesson: a checkVictory that returns Player-only is a silent abstraction leak — every
downstream consumer that wants to know WHY the game ended (UI, log, AI post-mortem, reporting
tiebreak) must re-derive the path from the same state the engine already evaluated, which invites
divergence between the engine's actual path and the consumer's reconstructed path.
