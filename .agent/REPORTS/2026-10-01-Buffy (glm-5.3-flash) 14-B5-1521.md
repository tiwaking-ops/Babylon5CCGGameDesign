# B5-1521 — offer-marker lifecycle proposal

## Scope and evidence

Claimed B5-1521 after the shared `run-queue.ps1 -DryRun` census and confirmed
the row was OPEN immediately after the tool-stamped claim. Read B5-1501's
measurement first and fenced its DONE row and report; no marker inventory was
repeated. Read `.agent/run-queue.ps1`'s selection and `Test-OfferMarkerAvailable`
implementation plus the prior B5-1441 audit/pattern.

B5-1501 measured 147 historical markers in the OS temp directory and four
offers in a `-DryRun -MaxIterations 20` run before candidates were rejected by
markers. Its report correctly noted it could not distinguish concurrent
lanes from PID reuse. The current code derives a per-ledger directory under
`[System.IO.Path]::GetTempPath()` named
`run-queue-offers-C__temp_projects_Babylon5CCGGameDesign__agent_TASK_LEDGER_md`
for this checkout, with one `<task-id>.offer` path per row. It stores only a
PID; live PID suppresses, dead PID is removed/retried, and malformed/nonpositive
PID uses a two-minute mtime bound. There is no completion-time cleanup.
`-DryRun` follows the same marker-acquisition path as normal mode, so it has
shared scheduling side effects even though it does not write ledger or claim
files. The queue selection marker remains distinct from the actual atomic
`.agent/CLAIMS/<task-id>.json` ownership record.

## Deliverable

Proposal: `docs/proposals/2026-10-01-offer-marker-lifecycle-contract.md`.
It specifies acquisition at candidate selection, non-truncating atomic
create-if-absent under a per-task gate, process identity beyond PID, release
only by matching run token after invocation, a pure default DryRun, bounded
legacy-marker recovery, and visible failure behavior. It explicitly leaves the
runner implementation and coordination files unchanged. The proposal names the
exact current B5-1521 marker path under `%TEMP%` as well as the marker-directory
pattern.

## Verification and bounds

- Boot census: `powershell -NoProfile -ExecutionPolicy Bypass -File
  .agent/run-queue.ps1 -DryRun` exited 0 and emitted 10 offers from 44
  claimable OPEN rows. Because DryRun currently uses the marker code path, the
  census was scheduling-active; no markers were manually touched.
- `javac -version`: 1.8.0_292.
- `sh b5ccg/compile.sh`: passed (65 sources; expected Java 6 bootstrap warning
  and existing unchecked note).
- `run-dup-census.ps1`: PASS, zero duplicate IDs.
- `ledger-query.ps1 -Status "*"`: own B5-1521 row reported pipeCount 7 and
  doubleLead no after close-out.
- Heartbeat validator remains red on pre-existing foreign store findings (16
  non-conforming entries and 3 identity collisions at boot); none was edited.

No queue script, claim other than this task's own lifecycle, foreign heartbeat,
source, card data, or marker file was edited. No commit or push.

**Reusable lesson:** a scheduler reservation needs an explicit acquisition,
release, and stale-recovery protocol; a PID and a marker file alone do not prove
who owns the reservation or when it is safe to clear it.
