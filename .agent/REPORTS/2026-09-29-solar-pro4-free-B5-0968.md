## Measured facts

### Card.java — the model-side cost field

- Line 25: `private int cost = 0;` — primitive `int`, default 0, no null possible.
- Line 67-68: `getCost()` returns the field; `setCost(int c)` does `cost = Math.max(0, c)` — negatives clamp to 0.
- No accessor exists today that reports whether the loader ever set the field; `getCost()` alone is the only cost API.

### DeckLoader.parseCards — the loader-side hydration (lines 97-101)

```java
String costStr = obj.get("cost");
if (costStr != null && costStr.length() > 0) {
    try { c.setCost(Integer.parseInt(costStr.trim())); }
    catch (NumberFormatException nfe) { /* keep default 0 */ }
}
```

Four JSON inputs all produce `getCost() == 0` and are **indistinguishable** at runtime:

| JSON input | Loader path | Resulting getCost() | Distinguishable? |
|---|---|---|---|
| key absent | `costStr == null` → skip | 0 | no |
| `"cost": ""` | `length() == 0` → skip | 0 | no |
| `"cost": "abc"` | NumberFormatException → catch | 0 | no |
| `"cost": "-3"` | setCost clamps to 0 | 0 | no |
| `"cost": "5"` | setCost(5) | 5 | yes (value-side only) |

So absent, empty-string, and explicit-zero are **three distinct JSON representations that all round-trip to the same model state**.

### B5-0335 cost entries — spot-check

Exact totals taken on trust from the B5-0335 report (read-only scope — this task does not recount). The material finding: the 6 explicit-zero cards are indistinguishable from the ~452 cards that never carried a cost key, because `parseCards` leaves both at `getCost() == 0` with no side channel.

## Answer

**A future backfill cannot distinguish legitimately-free (cost 0 by design) from never-costed (no key yet) from the current model side.** This is the blocker the B5-0961 plan names.

The runtime equivalence is not a bug in the existing loader — it is the correct backward-compatible behaviour for B5-0323 (absent → 0 preserves the pre-cost field semantics). But it means the loader's *knowledge* that a key was present is discarded, and that knowledge is exactly what a backfill author needs to decide whether `0` means "free by design" or "not yet costed".

## Smallest preserving schema change (proposal only — no implementation on this row)

Add to `Card`:

```
private Boolean costSpecified = false;
public boolean costSpecified() { return costSpecified == null ? false : costSpecified; }
```

And in `DeckLoader.parseCards`, set it true only on the successful parse path:

```
if (costStr != null && costStr.length() > 0) {
    try {
        int v = Integer.parseInt(costStr.trim());
        if (v >= 0) { c.setCost(v); c.setCostSpecified(true); }
        // negative: keep default 0, leave costSpecified false
    } catch (NumberFormatException nfe) { /* keep default 0, false */ }
}
```

Rules:

- `costSpecified` defaults false on every new Card (backwards-compatible for all pre-existing construction paths).
- It is set true **only** when the loader parsed a present, non-empty, non-negative integer from a `cost` key — i.e. exactly when the JSON author explicitly provided a cost.
- It is NOT set for `"cost": "-3"` (negative clamped to 0 but not specified-as-valid) and NOT set for absent/empty/non-numeric.
- All existing arithmetic (`getCost()`, sponsorCost, promotionCost, build INFLUENCE) continues reading `getCost()` unchanged — this is a metadata predicate, not a value substitute.

Effect on the existing data (no JSON touched):

- 452 unbackfilled cards → `cost=0, costSpecified=false` (never-costed).
- 377 B5-0335 cards that carried a present non-negative cost → `costSpecified=true` (cost specified by the backfill author), including the 6 explicit `"cost": 0` cards (legitimately free, flagged as specified).
- The 6 explicit-zero cards become distinguishable from the 452 unbackfilled: `cost=0, costSpecified=true` vs `cost=0, costSpecified=false`.

This satisfies B5-0961's stated constraint ("the schema may have no null cost") because the model already carries no null — `cost` is primitive `int` and `costSpecified` is a Boolean predicate, not a nullable cost. No null cost enters the schema.
