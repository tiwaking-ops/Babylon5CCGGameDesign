## The actual fixture shape (the new finding)

Both disagreements are on **one** row, `B5-0481`, and both are the *same* root
cause wearing two rules:

* `.agent/CLAIMS/B5-0481.json` declares `"agent_id": "solar-pro4"`.
* The only solar heartbeat on disk is `solar-pro4-free.json`, whose own
  `agent_id` field reads `solar-pro4:free`.

`Get-NormName` strips colons and dashes, so:

```
Get-NormName('solar-pro4')      -> 'solarpro4'
Get-NormName('solar-pro4-free') -> 'solarpro4free'
Get-NormName('solar-pro4:free') -> 'solarpro4free'
```

The claim's owner `solar-pro4` normalises to `solarpro4`; the file on disk
normalises to `solarpro4free`. **Distinct keys.** So `ledger-query.ps1` finds no
heartbeat for that owner and returns `UNKNOWN` (its absent-signal rule), while
`run-queue.ps1` falls back to claim age and returns `stale`. The row `B5-0481` is
in fact **`DONE`**, with a report dated 2026-09-26, and its claim file is still
on disk - an orphan claim, the same shape B5-0777 declined to reap.

So the divergence is not a logic drift between the two tools. It is **one
foreign claim whose `agent_id` names an agent that does not exist under that
spelling**, and the two tools are each obeying their own documented rule about
what to do when the owner signal is missing.

## Proof by fixture: make the owner resolve, and the tree goes green

Dropping a single fixture heartbeat `solar-pro4.json` (`agent_id: solar-pro4`)
into a **temp** heartbeat directory and re-running the *unmodified* live tool
against the same live ledger and claims:

```
census-crosscheck: CONSISTENT -- 432 row(s), run-queue and ledger-query agree.
exit 0
```

All 432 rows, zero disagreements. The two census tools agree **completely** once
the owner id resolves to a heartbeat. That is the sharpest statement of the
fixture shape available: the cross-check is not detecting tool drift; it is
correctly reporting that a claim's owner string is unresolvable.

This also re-confirms the B5-0775 conclusion from the other side - the fix
remains in place, the tool still goes green when it should, and no false red was
introduced.

## Reusable lesson

**A red cross-check names a disagreement, not a cause - and the cheapest way to
learn which is to subtract the fix you suspect rather than subtract `HEAD`.**
Removing exactly the four lines a prior task added, from a copy of the current
tree, turned a plausible hypothesis into a measurement: the B5-0775 fix was
innocent and the red was one unresolvable owner id. Then the decisive test was
not another removal but an **addition** - dropping in the missing heartbeat as a
fixture turned all 432 rows green, which located the fault in the *data* rather
than in either tool's logic. When a checker is red, ask what single fact, if it
changed, would make it green, and change exactly that in a temp tree; the shape
of the answer is the fixture shape the owner needs.

`$reportsL.ContainsKey($taskId)` third-signal fold inside `Get-Verdict-L`, with
the explanatory comment above it.
