## What was changed

Rulebook V. establishes "Rotate to Build Influence" as a core Action-Round
action (Influence Rating ≤ 9; rotate an Inner Circle character; spend 3
influence; rating goes up by 1; ≥ 10 cannot). This task wires that action
end-to-end with the smallest possible surface: one new `GameAction.Type`, two
public methods on `RulesEngine`, one switch branch on `GameController`, and a
legal-action offer + score in `AIPlayer`.

### 1. `model/GameAction.java` — new type + factory

Added `BUILD_INFLUENCE` to `GameAction.Type` enum (order: PLAY_CARD,
INITIATE_CONFLICT, JOIN_CONFLICT_SUPPORT, JOIN_CONFLICT_OPPOSE,
PLAY_AFTERMATH, RECRUIT_CHARACTER, **BUILD_INFLUENCE**, PASS — placed after
RECRUIT_CHARACTER to keep the new action adjacent to the other character-faction
action, before PASS which must remain final for readability).

Added a matching factory:

```
public static GameAction buildInfluence(CharacterCard leader)
    { return new GameAction(Type.BUILD_INFLUENCE, leader, null); }
```

The factory takes the leader (the rotating IC character) as its lone non-null
argument; `target` is null because Build Influence is solo — no opponent or
supporting card is involved.

`toString()` updated via `StringBuilder` (Java 6 compatible) to emit
`BUILD_INFLUENCE: <card title>`.

### 2. `engine/RulesEngine.java` — legality + execution

Two new public methods, both guarded by the rulebook constraints.

`canBuildInfluence(Player p)` → boolean. Returns true exactly when:

- `p.getInfluence() >= 1` (a faction begins at 4; this guards against
  degenerate 0-influence state that should not occur in normal play, but is
  cheap insurance);
- `p.getInfluence() <= 9` (rulebook VI.: a faction with Rating ≥ 10 may not
  Build Influence);
- at least one `CharacterCard` in `p.getInnerCircle()` is unrotated.

`executeBuildInfluence(Player p, CharacterCard leader, GameState state)` →
void. Preconditions re-checked inside the method (so the engine is safe even if
the AI offers a stale action):

- calls `canBuildInfluence(p)`;
- checks `leader` is in `p.getInnerCircle()`;
- checks `leader.isRotated() == false`;

then performs the action: `leader.rotate()`, `p.loseInfluence(3)`,
`p.gainInfluence(1)` (net pool change = −2, rating goes up by 1 as the rulebook
requires), and logs:

```
<player> builds influence: <leader title> rotates, rating now <rating>
```

Side-effect failures log a diagnostic and return without corrupting state (a
stale/stale-offer defense, not an expected path).

### 3. `engine/GameController.java` — processAction switch

Added a `BUILD_INFLUENCE` branch to the existing action-type switch inside
`processAction()`:

```
case BUILD_INFLUENCE:
    if (action.getCard() instanceof CharacterCard) {
        CharacterCard leader = (CharacterCard) action.getCard();
        rules.executeBuildInfluence(p, leader, state);
    }
    break;
```

No new phase, no new UI callback path — the engine already logs every action via
`state.log(p.getName() + ": " + action)` before the switch, so Build Influence
turns appear in the log naturally as e.g. `Delenn: BUILD_INFLUENCE: Lennier`.

### 4. `ai/AIPlayer.java` — legal offer + scoring

`buildLegalActions()` extended: after the hand-loop that offers PLAY_CARD /
INITIATE_CONFLICT / RECRUIT_CHARACTER, the AI now offers Build Influence
whenever `p.getInfluence() <= 9` and at least one unrotated IC character exists.
Each ready IC character produces one `GameAction.buildInfluence(ch)` action.

Note: the scope's existing `GameState` has no per-round conflict count and
`GameController` does not call `rules.canInitiateConflict()` today;
B5-0203's D2 fix (blocking re-initiation) is still the authoritative defense
against duplicate-conflict-offer and is NOT re-created here. B5-0301 therefore
touches only the Build Influence path and leaves D2 untouched.

Scoring:

- **MEDIUM / scoreActionMedium**: BUILD_INFLUENCE returns `3 + remaining` where
  `remaining = max(0, 10 - p.getInfluence())`. So at influence 4 the action
  scores 9 (comparable to Agenda at 8, Location at 6), at influence 9 it scores
  4. Rationale: Building Influence is always net-positive (rating goes up,
  action economy is the only cost, and a lower rating is a permanent handicap),
  so MEDIUM should prefer it to a plain Event play (score 2) but not to a
  strong Agenda play.

- **HARD / scoreActionHard**: BUILD_INFLUENCE returns `0.25 * max(0, 10 -
  p.getInfluence())` — a small positive in [0.0 .. 2.25]. HARD already weights
  conflicts (base + leaderBonus + lossPenalty), recruit-by-stat (4 + maxStat *
  0.5), and permanent plays (Agenda 9, Location 7, Group 5), so a fractional
  Build Influence score keeps it from dominating the table. The cap-aware factor
  means the AI treats Build Influence as more attractive the closer it is to the
  10-rating ceiling, which matches the rulebook's gate: once at 10 the action
  disappears entirely.

- EASY offers the action but never special-cases it (random from the legal list,
  with the existing 30% pass bias). This is intentional — EASY is not expected
  to be strategic, only to exercise the action so it appears in the smoke test.

## Edge cases handled

- AI offers Build Influence at influence 10+ → not offered (canBuildInfluence
  returns false; buildLegalActions guards with `p.getInfluence() <= 9`).
- Player has 0 influence (should not happen in normal play) → not offered.
- Player has IC characters but all rotated → not offered.
- Player has no IC characters (e.g. deck-out forfeiture path) → loop over
  `getInnerCircle()` is empty → not offered.
- Stale action passed into processAction (leader already rotated, leader not in
  IC, or player suddenly ineligible) → executeBuildInfluence re-checks and
  returns after logging; state not corrupted.
- `GameState` lacks per-round conflict tracker → not relevant to Build
  Influence; B5-0203 D2 remains the conflict-reinitiation defense.
