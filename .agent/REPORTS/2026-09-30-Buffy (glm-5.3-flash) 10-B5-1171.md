# B5-1171 — two guards close the UI's cheapest door on the character-discard path

Agent: `Buffy (glm-5.3-flash) 10`, javac `1.8.0_292`. Scope: `MainWindow.java`
only (two hunks), one report, one pattern, one heartbeat, one DECISIONS entry.
**No engine file touched, no ai or card-data edit, no commit, no push.**

## Premise (inherited from B5-1109's report, re-stated)

B5-1109 measured by scratch probe that `applyGenericCardPlay`
(`GameController.java:630-684`) charges `card.getCost()` raw and, for a card
that is not an Enhancement/Location/Group/Agenda/Event, **discards it**. A
`CharacterCard` dispatched as a generic play is therefore charged raw (not the
sponsor cost), removed from hand, and never seated in the supporting role.
B5-1109 further read from source that `MainWindow.playOnly` refuses only
`ConflictCard` and that the "Play Card" enable predicate does not exclude
characters — so a selected in-hand character *can* reach the corrupting
dispatch through the button.

## The fix (the smaller of the two fixes B5-1109 recommends)

1. **`playOnly()` refuses characters.** The early return now reads
   `selectedCard == null || instanceof ConflictCard || instanceof CharacterCard`,
   with the B5-1109 rationale in the comment. Even if some future caller
   dispatches the action, the button's own handler refuses it the way it has
   always refused conflicts.
2. **The `canPlay` enable predicate never lights for a character.** Added
   `&& !(selectedCard instanceof CharacterCard)`. The enable gate read turn,
   phase, hand membership, and agenda lifecycle but **no type route**; a lit
   Play on a character could only ever reach the corrupting generic dispatch,
   so characters never light it now. Refuse-and-never-offer, not
   offer-then-refuse.

Sponsor and Promote remain the character routes; both already gate on
`canRecruit`/`canPromote` (B5-1121 verified this seam at both moments).
