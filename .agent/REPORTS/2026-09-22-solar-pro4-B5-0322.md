# B5-0322 — human join/support/oppose conflict path (engine side)

**Verdict: DONE.** Wired `JOIN_CONFLICT_SUPPORT` / `JOIN_CONFLICT_OPPOSE` through
the engine so a human player can join an active conflict from either side via
`submitHumanAction()`. AI join path untouched.

## What changed (engine/ only)

### RulesEngine.java — two new methods

- `canJoinConflict(Player p, Conflict conflict)`:
  - returns false if p has passed
  - returns false if p has no actions left
  - returns false if conflict is null
  - returns false if conflict is already resolved
  - returns false if p is already a participant
  - otherwise true
- `executeJoinConflict(Player p, Conflict conflict, boolean support, GameState state)`:
  - re-checks `canJoinConflict` (stale-offer defense — mirrors B5-0301 pattern)
  - calls `conflict.addParticipant(p, support)` — the existing side API from B5-0309
  - commits p's face-up ambassador via `conflict.commitCard(p, ambassador, support)`
    if present (matching the AI join pattern in `resolveCurrentConflict()`)
  - logs the join with side label

### GameController.java — processAction switch cases

- `JOIN_CONFLICT_SUPPORT`:
  - if no active conflict: logs "No active conflict to join."
  - if active conflict but `canJoinConflict` false: logs "cannot support — join not allowed."
  - if join allowed: calls `rules.executeJoinConflict(p, conflict, true, state)`
- `JOIN_CONFLICT_OPPOSE`:
  - identical structure with `support=false`

The `submitHumanAction(GameAction)` path was already wired (line 270): a human
caller builds a `GameAction` with the appropriate type and submits it; the
background thread's `waitForHumanAction()` returns it and `processAction` runs it.
