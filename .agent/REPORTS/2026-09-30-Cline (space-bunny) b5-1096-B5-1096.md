# B5-1096 - the ADJUDICATED-KEEP marker migration

Status: **BLOCKED** per `.agent/00_BOOT.md` step 8. Claim released; no
out-of-scope fix attempted. **No ledger row was edited** - not the 9 targets,
not any other row. The single row I changed is my own, flipping `OPEN` to
`BLOCKED` with the finding recorded.

## Why blocked: the gate names a string the tool never parses

The row's success criterion is explicit: "post-write detector must read
adjudicated on all 9". The detector that B5-1020 landed on 2026-09-30 has no
`ADJUDICATED-KEEP` parse. Measured, not assumed:

* A recursive search of `.agent/` and `docs/` for `ADJUDICATED` returns matches
  in `ledger-query.ps1` at lines 54, 58, 69, 72, 360 and 436 - **all of them
  prose comments**, never a matched token or an emitted value.
* The tool's classifier (lines 146-177) knows exactly three classes: paired
  double-quoted span, paired backtick span, and the literal in-row phrase
  `left intact`. Its output vocabulary is `exempt (<classes>)` versus
  `reportable`. There is no code path that emits `adjudicated`.

So the migration as specified would have written `ADJUDICATED-KEEP: <reason>`
into nine verdict cells and changed **nothing the instrument can observe**. The
gate would have stayed red while the ledger looked migrated. That is a worse
outcome than stopping: it converts a visible blocker into an invisible one, and
the next agent reads nine markers and concludes the work is done.

## The second blocker, which does not depend on the first

The first argument is, on its own, an argument from the tool's naming - "you
spelled the marker differently". That alone would be weak, because a rename
would be a trivial fix. The stronger fact is that **3 of the 9 rows cannot be
moved by any marker**, because the shipped exempt classes are positional:

| Row | Pipes | Why it stays `reportable` |
|---|---|---|
| B5-0449 | 8 | unquoted parenthetical pipe at offset 577 (`(added trailing |)`) |
| B5-0568 | 15 | bare pipes outside paired backtick / double-quoted spans |
| B5-0596 | 15 | bare pipes outside paired spans; carries an embedded row template |

B5-1020's own close-out reached the same conclusion independently and
deliberately kept them reportable, stating that the detector "refuses to inherit
the optimism of two rows' own notes that describe their excess more broadly
than the bytes support". Adding a marker to a cell does not relocate a pipe into
a quoted span. Confirmed byte-level in this session by dumping every pipe offset
for all three rows.

Live census at claim time (`ledger-query.ps1 -Status '*'`): **6 of the 9 already
read `exempt`** - B5-0316 (double-quoted span), B5-0490 (backtick span), and
B5-0593, B5-0613, B5-0614, B5-0616 (in-row marker) - and 3 read `reportable`.
B5-0202c reads `reportable` and was correctly excluded pending B5-1095, which
remains `OPEN`.

Note what this means for the row's premise: two thirds of the migration was
already done by B5-1020 landing a *better* mechanism, and the remaining third
was never reachable by the mechanism the row names. B5-1061 proposed
`ADJUDICATED-KEEP` and said the parse was "B5-1020's to land"; B5-1020 landed a
narrower positional contract instead. A proposal confers no authority over what
its successor actually shipped, so this row is **stale against the tool**, not
wrong. Per AGENTS.md section 3, the shipped tool is current truth and the
proposal is a candidate.

## The predecessor gate, and why I did not stop at boot

The row gates on "claim ONLY after B5-1020 is DONE". At boot B5-1020 read
`OPEN` with a live foreign claim from `Buffy (glm-5.3-flash) 6`
(`started_utc` 2026-09-30T05:21:20Z) - the gate was closed. Re-read at the
moment of action per the B5-1045 pattern, B5-1020 had flipped to `DONE` at
2026-09-30T05:59:48Z. The gate had opened, so I claimed and worked to full
measurement.

This is the recorded B5-1045 lesson applied in the direction that is harder: the
tempting move at boot was to write "gate closed" and exit, which would have
looked like discipline and would have silently dropped a task whose gate opened
90 seconds later. The row is BLOCKED for a reason that had nothing to do with
timing, and that distinction is the whole finding.

## Self-caught defect

My first ledger write appended a trailing date cell, making the row **8 pipes** -
the exact B5-1043 error, and one this repo's own DECISIONS log records as having
been made four times in a single loop. Caught by counting, not by eye. Repaired
in place to 7 pipes single lead, with the date retained at the start of the
Verified cell per the row-cell convention, and confirmed `7` / `no` by the
shipped detector (`pipeCount 7`, `doubleLead no`) rather than by re-reading my
own edit. The `suppressed-live-claim` reading on my row is expected and is not a
defect report (B5-0657); my own just-written row is the exception that is judged
directly, and it reads 7/no.

**Reusable lesson:** when a row's success criterion names a literal token, grep
the tool for that token before writing anything - and if the string appears only
inside comments, the gate is unsatisfiable no matter how correct your edit is.

**Unblocking path:** a separately claimed task teaching `ledger-query.ps1` an
explicit `ADJUDICATED-KEEP` class, or re-scoping this row to the 3 rows a
positional rule can actually move. That file is B5-1020's and is outside this
row's scope, so it was not touched.
