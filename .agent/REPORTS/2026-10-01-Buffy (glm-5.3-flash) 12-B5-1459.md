# B5-1459 — does any deck derivation path depend on 60-card starter arithmetic?

agent_id: Buffy (glm-5.3-flash) 12 · task: B5-1459 · date: 2026-10-01 · javac: 1.8.0_292
Scope honored: read-only engine + deck data; no deck JSON, card JSON, or src edit; no commit.

## 1. Where the 60-per-deck invariant lives (measured)

**Data side — `b5ccg/resources/decks/premiere-starter-decks.json`** (187 rows, 4 decks):

| deck | entries | sum of `count` | distinct ids | dup (deck,id) rows |
|---|---|---|---|---|
| HUMAN | 48 | **50** | 48 | 0 |
| CENTAURI | 47 | **50** | 47 | 0 |
| MINBARI | 47 | **50** | 47 | 0 |
| NARN | 45 | **50** | 45 | 0 |

The 50-card fixed side is exactly at target in data, with zero duplicate rows.

**Code side — constants 50/60/55, derived vs hardcoded:**

* `StarterDeckBuilder.java:49-51` — `FIXED_TARGET = 50`, `RANDOM_COUNT = 10`,
  `DECK_SIZE = FIXED_TARGET + RANDOM_COUNT`. **The only derived 60 in the tree.**
  Fixed-count miss (`fixedCount != FIXED_TARGET`, lines 133-136) prints to
  **stderr and does not throw**; the deck is still built.
* `Main.java:141,149,152` — fallback builder hardcodes literal `60` three times
  (`deck.size() >= 60`, `< 60`, `subList(0, Math.min(60, deck.size()))`). Hardcoded.
* Probe fallback builders hardcode `< 60` filler bounds:
  `HeadlessSmokeTest.java:275,291`, `HeadlessMultiRoundTest.java:310,324`,
  `HeadlessStallSoakProbe.java:293,307`, `HeadlessReportingTiebreakTest.java:562,576`.
* `55` — **appears nowhere** in `b5ccg/src`.
* `GameController` — **carries no deck-total reference at all**: only `drawCards`
  call sites (opening draw of 3 at line 81 assumes nothing about deck size).
  The runtime engine never validates deck size; exhaustion is handled by the
  D8 deck-out penalty regardless of initial size.

## 2. Would any path silently accept a 59-card deck? YES — every path

1. **Data shrink to 49**: `fixedCount = 49` → stderr warning only → deck = 49 fixed
   + 10 random = **59, built without error**.
2. **Random-side shortfall**: `drawRandomUncommonsRares` pads to `RANDOM_COUNT`
   while candidates remain; if the candidate set is **empty** (no playable
   UNCOMMON/RARE) it returns fewer **with no warning at all**.
3. **Fallback builders** (`Main.java`, four probes): fill up to 60 and cap with
   `min(60, size)` — a smaller pool yields a smaller deck silently.
4. **Engine/consumers**: no assertion on deck size anywhere; a 59-card deck
   plays identically.

## 3. Which existing probe would catch it

`HeadlessConformanceTest.testDeckConstruction()` — the **CVD** block (B5-0606,
lines 2078-2158) reads the same deck JSON via
`DeckLoader.loadFlatObjects(StarterDeckBuilder.DECK_RESOURCE)` and asserts per
deck: `total >= 45` (II:193), `maxCopies <= 3` (II:194), exactly one Starting
Ambassador (II:195), for all four races.

**Gaps:** the CVD floor is **45, not 50** — a deck dropping 50→49 (or →46)
still passes; and CVD reads the **JSON, not the built deck** — it never
exercises `StarterDeckBuilder.build`, so the stderr-only fixedCount path and
the `RANDOM_COUNT = 10` assembly are unprobed. No probe anywhere asserts a
built deck's size (the only `60`s in src are filler-loop bounds).

## 4. Deterministic slice handed to OPEN B5-1331

Deck-total arithmetic is **frame-independent**: the deck JSON side is exactly
50×4 with zero duplicate rows regardless of the 829-record raw frame vs the
446-title deduped pool frame (fixed lists resolve Premiere ids with a
Deluxe-title fallback, per `findFixedByTitle`). Therefore any pool-frame vs
raw-frame cost divergence B5-1331 reconciles **cannot originate from
deck-total arithmetic** — it lives entirely in card-record cost fields.
B5-1331 can treat the deck-JSON totals as a fixed control (50×4, re-measurable
in one pass) rather than a variable.

## Reusable lesson

An invariant enforced only by a stderr warning is not a gate: the 60-card
starter invariant is derived in exactly one place, hardcoded as literals in
five more, asserted at floor 45 by a data-only probe, and unchecked by the
entire runtime — any single point of failure audit must name which of those
layers it is actually testing.
