# B5-0452 — Initiation-targeting fix slice (B5-0451 findings)

## Verdict

DONE. The B5-0451 F1 (MEDIUM-HIGH) and F2 (MEDIUM) defects are closed and
the F3 recommendation executed, in one file (b5ccg/src/b5ccg/ui/MainWindow.java),
three hunks, ui/ only, no game-logic change.

## Changes

1. **Listener guard (F1):** new field `targetSelectorPopulating`; the
   target-selector listener early-returns while it is set. The population
   block in `applyCardSelection` wraps `removeAllItems` + `addItem`s in a
   Java 6 `try/finally` (B5-0102 precedent; the ban is on
   try-with-resources, which `try {` is not), then clears the flag and
   sets `selectedTarget = null`. The JComboBox auto-selection during
   population now fires nothing; only a genuine user change event sets the
   target — the B5-0325 explicit-choice gate finally means what it says.
2. **Stale-target reset (F2):** `applyCardSelection` clears `selectedTarget`
   on every conflict-card (re)selection, so a target picked for one conflict
   can no longer satisfy `targetReady` for the next.
3. **Dead fallback removal (F3):** the unreachable highest-influence
   auto-target fallback in `initiateOnly` is deleted; dispatch now submits
   only an explicit user-picked target (and still returns safely on null).

F4 (phase breadth) was deferred by B5-0328 and is untouched; F5 stands
(engine validates all submissions).

## Reusable lesson

Fix the widget's firing behavior, not just the gate that reads it: an
explicit-choice gate over a Swing selector is only as honest as the
population window — guard the population (suppress + try/finally), reset
the chosen value on every source change, and delete fallback paths the
gate already made unreachable instead of maintaining dead intent.
