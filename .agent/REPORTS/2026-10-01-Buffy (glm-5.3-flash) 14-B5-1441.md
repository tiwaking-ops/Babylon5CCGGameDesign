# B5-1441 — run-queue offer behavior audit

## Scope and method

Read-only audit of `.agent/run-queue.ps1` and the live queue. No runner, ledger,
claim, or foreign heartbeat was edited. `javac -version` is 1.8.0_292;
`sh b5ccg/compile.sh` passed (65 sources, `-source 6 -target 6`, expected
bootstrap warning). Compile is a no-change regression check, not evidence about
PowerShell behavior.

## Actual offer rule

`Get-ClaimableOpenTasks` builds its offer set in this order: parse ledger rows;
select `OPEN`; exclude claim IDs already in `Get-CensusSuppression`; exclude
B5-0653/B5-0952 implausible timestamp claims; call `Test-LiveClaim`; enforce
hard-coded prerequisite IDs and the historical 0367–0381 lane occupancy table;
then sort by numeric task ID. For each picked candidate, `Select-OfferRow`
rotates by `$PID % candidate-count`, skips IDs already offered by this process,
and tries an OS-exclusive `.offer` marker in `%TEMP%`. Successful marker creation
is the offered row; a live marker owned by another process causes the selector
to walk to the next candidate. The actual claim remains the later agent's
separate atomic claim-file creation: marker ownership is offer scheduling, not a
claim.

Normal mode invokes one agent per iteration and samples the DONE count before
and after invocation. It stops at no candidate, `$MaxIterations` (default 10),
or `$BlockedStreakLimit` (default 3 iterations without a DONE flip). DryRun
still acquires offer markers and records rows in `$offeredThisRun`, then prints
"would invoke" and continues. Thus a dry run is read-only with respect to the
ledger and claims, but not observationally pure: it can influence a concurrent
runner's offer selection for as long as its process and offer markers survive.
The run-queue dry run repeatedly offered eight distinct items then reported
that every claimable row had been offered; it did not test a subprocess lane
race, marker cleanup, or any mutation window.

## Adversarial cases

- **Stale-dated claim on an OPEN row:** when no owner heartbeat or report is
  fresher, the shared three-signal calculation makes the claim stale, so the row
  is eligible to enter the free set. This is consistent with the live census
  contract; the runner itself does not reap the file. A parseable timestamp over
  60 minutes ahead is instead excluded by the B5-0952 refusal. `Get-CensusSuppression`
  treats any future started_utc as suppression (fail-safe, not a liveness verdict),
  while the offer path refuses it; result is withheld rather than offered.
- **Row under a future-dated claim:** for >60 minutes ahead, the primary scan
  warns and excludes it, and `Test-LiveClaim` also returns unstealable. Within
  tolerance, a fresh owner heartbeat means it remains live. The helper was
  checked in a non-mutating dot-source probe: +30 minutes returned no refusal;
  +90 returned 90 minutes of overshoot. The fixture did not invoke offer-path
  warnings against real claims.
- **Claim vanishes between census and offer:** claimability is measured while
  `Get-ClaimableOpenTasks` builds `$free`; there is no final claim-file recheck
  in `Select-OfferRow`, just a TEMP offer-marker check. If another owner removes
  a claim after the candidate census, this runner may offer the now-free row,
  which is harmless if the ledger row is still OPEN and the agent's later
  atomic claim succeeds. If another agent writes a claim in that interval, the
  offer can be stale; the recipient must obey the task prompt and recheck claim
  absence immediately before claiming. An existing claim is never overwritten
  by the offer marker.
- **Row flips DONE after offer selection:** the ledger status is not re-read
  between candidate selection and invoking the CLI. The recipient prompt
  explicitly requires re-reading the row and confirming it remains OPEN before
  creating a claim; a DONE row therefore makes the offered prompt stale, not a
  license to work it. No live row was mutated to stage this case.
- **Double offer / two runner processes:** PID-offset selection is only
  diversification; the per-row exclusive marker is the concurrency mechanism.
  Its `IOException` loser walks the candidates. If TEMP setup or marker IO
  raises another error, the broad catch returns available (fail-open), so a
  simultaneous offer can still occur under infrastructure failure. The atomic
  claim file remains the final collision guard.

## Smallest hardening ideas (not applied)

1. Make `-DryRun` avoid creating shared `.offer` markers (or clearly separate
   a pure census preview from the current scheduling dry run), so previews do
   not contend with live offers.
2. Immediately before printing/invoking the chosen task, re-read its ledger
   status as OPEN and test claim absence; if either changed, discard the choice
   and re-census. This narrows the stale-offer window but cannot eliminate the
   race after the final check, so atomic claim creation remains mandatory.
3. Preserve the existing exclusive-create arbitration on expected IO race, but
   make unexpected marker infrastructure failures visible and stop/fall back
   to a bounded non-shared offer path rather than silently fail-open.

## Verification and bounds

`ledger-query.ps1 -Status OPEN` confirmed my own B5-1441 row was seven pipes,
single-lead, and suppressed under my live claim. The shared run-queue census
ran read-only. `run-dup-census.ps1` passed with zero duplicate IDs. Heartbeat
validator has pre-existing unrelated schema findings/collisions; foreign files
were left byte-identical. No `.agent/run-queue.ps1` change, no src/data change,
no foreign coordination mutation, no commit or push.

**Reusable lesson:** an offer marker schedules a candidate; only the claim file
claims it, so a candidate must be revalidated at claim time and every dry-run
must state whether it also participates in shared offer scheduling.
