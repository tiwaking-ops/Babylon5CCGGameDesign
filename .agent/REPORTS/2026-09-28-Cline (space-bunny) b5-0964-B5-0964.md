## GameBoardPanel.java — 3 hunks

### Hunk 1 — `+import b5ccg.model.CivilWarState;` — **cosmetic**

Strictly **redundant**: the file already carries `import b5ccg.model.*;` one line
later, which already covers `CivilWarState`. It compiles, it is Java 6-legal, and a
single-type import beside a wildcard violates nothing in `AGENTS.md` §2. Left alone
deliberately — the row forbids `b5ccg/src` edits, and "remove a redundant import" is
exactly the kind of drive-by that turns a certification row into an unreviewed diff.

### Hunk 2 — computed-Power readout — **readout, no behaviour change**

Calls `p.getPower()` and `p.getPowerBonusTotal()` and renders
`"Power: N (inf M ± B)"`. `Player.getPower()` (`Player.java:78-79`) is defined as
`influence + getPowerBonusTotal()` — **derived, never stored**, so the UI is reading a
computed seam and cannot desynchronise from it. The row's stated intent ("shown only
when the two actually differ", guarded by `power != p.getInfluence()`) is honoured, so
a board with no POWER-tagged card in play is not cluttered. This is the B5-0677 seam
the row names, and conformance asserts it under `[PWR]`.

Placement is the RIGHT of the name row (`x + w - 108, y + 33`) and the comment explains
why (the left column below `y + 58` belongs to the ambassador mini-card).
`x + w - 108` can go negative on a very narrow zone with 3+ players
(`zoneW = getWidth() / players.size()`, `GameBoardPanel.java:216`) — a *clipping* risk,
not a correctness one. Cosmetic, recorded, not fixed.

### Hunk 3 — Unrest + Civil-War readouts — **readout, with one cosmetic overlap**

The `unrest > 1` guard matches `Player`'s own semantics: `unrest` starts at 1
(`Player.java:60`, rulebook `:278`) and is clamped to 1..5 (`:428`, `:430`, rulebook
`:280`), so a baseline 1 is correctly suppressed and a NON_ALIGNED player's starting 2
(`Player.java:66`) correctly shows.

`state.civilWarOfRace(p.getFaction())` is **race-level** (`GameState.java:93-94`, a
`LinkedHashMap<Faction, CivilWarState>`), so both players of a warring race show
`CIVIL WAR` — correct under the B5-0691 race-level matrix, which conformance asserts
under `[CWR]`.

**Cosmetic finding (recorded, not fixed):** both new labels draw at `x + 8, y + 47` —
the *same* origin as the pre-existing faction string on line 438
(`g.drawString(p.getFaction().toString(), x + 8, y + 47)`). So the faction name is
overpainted by `Unrest: N`, and then overpainted again by `CIVIL WAR` when both
conditions hold. This is a **paint-order overlap in one zone header**, not a behaviour
change: no state is read that was not already readable, and nothing is derived. Note
the contrast with hunk 2, whose comment shows the author *did* reason about the
ambassador mini-card collision and picked a different origin for the Power line — the
two new labels were simply placed on the last free-looking row. Out of scope to fix
under this row.

### Engine-authority check (the substantive part)

`refreshSurrenderControl` does **not** re-derive legality. It iterates
`state.getPlayers()` and asks `RulesEngine.canSurrender(human, p, state)`
(`RulesEngine.java:821-834`) once per candidate, then renders the answer. The one
guard it adds on its own — `!human.hasSurrendered() && !human.hasForfeited()` — is
already a conjunct inside `canSurrender` (`:823`), so it is a narrowing that can never
widen the engine's verdict: an empty list is what the engine would have said anyway.
That is the B5-0423 heal/repair lesson applied correctly.

### Two cosmetic findings in the helpers (recorded, not fixed)

- **The hint/tooltip can name a different player than the selection.**
  `refreshSurrenderHint` renders `legal.get(0)` — the *first legal* target — while the
  combo can hold several and the user may have selected any of them. So the `+3`
  readout and the `inf X -> Y` tooltip can describe player A while the submission
  would go to player B. The **commit path is unaffected** (it resolves
  `selectedSurrenderTarget()` and the engine re-checks), so this is a misleading
  label, not a wrong action. It is also transient: the next full refresh resets the
  selection to index 0 and the hint re-agrees.
- **Round-phase wording.** The empty-list tooltip says "during the draw round" where
  the rulebook says "discard round" (`:817`). `GamePhase.DRAW` is the engine's constant
  for that phase, so the UI names the engine accurately; a player reading only the
  printed rulebook would have to make one translation. Cosmetic.

### Java 6 conformance of the diff

`java.util.List` / `java.util.ArrayList` are **fully qualified** rather than imported —
legal, verbose, Java 6. No diamond, no lambda, no method reference, no
`computeIfAbsent`, no try-with-resources. `@Override` on `actionPerformed` in an
anonymous `ActionListener` is legal from Java 6 onward. The single `->` grep hit in
`ui/` is inside a **string literal** (`:1745`, tooltip text `" -> "`), which is exactly
the case the Java 6 grep must distinguish from a lambda arrow; it is not a construct.
