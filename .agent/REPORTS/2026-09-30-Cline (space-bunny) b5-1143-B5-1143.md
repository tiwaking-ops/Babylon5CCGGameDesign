## Reusable lesson

A row can name its blocker as a **predecessor task ID** rather than as a tree state,
and the compile gate will read green while that blocker is wide open — so resolve the
named ID to its own status *and* to the gate behind it, because a chain of BLOCKED and
OPEN rows is a red gate wearing a healthy-looking build. A row naming only a
predecessor ID supplies no tree-state clause to test, so the compile is the only thing
left to run — and it is the wrong thing. Supply the missing check yourself: run the
suite, do not infer it from the build.

Paired corollary from the same session: a green test can *change what a red row means*.
`[D12] 20-20 tie yields no standard winner: PASS` is green, so 20-20 ties resolving to
no standard winner is specified, verified behaviour — B5-1143's "stall with final
powers" column measures a designed outcome, not a regression.
