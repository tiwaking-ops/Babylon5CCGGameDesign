# B5-0468 — Opponent-targeted enhancement model seam

**Verdict: DONE — model seam only, zero engine wiring, zero behavior change.**

## What was done

Promoted the Censure-class fleet-penalty "attach to a chosen opponent's
fleet" from a comment-only stub in `CardEffects.java:209` to a real model
seam in `b5ccg/src/b5ccg/model/`. No engine wiring, no behavior change, no
resources edits.

### EnhancementCard.java

Added two fields and four accessors:

- `targetCardId` (String) — card id of the intended target; null/empty =
  self-target semantics (legacy behavior).
- `targetOwnerName` (String) — name of the player who owns the intended
  target.
- `setOpponentTarget(cardId, ownerName)` — records the intended target
  identity.
- `getTargetCardId()` / `getTargetOwnerName()` — read accessors.
- `hasExplicitTarget()` — true when this enhancement carries an explicit
  target identity rather than the legacy self-target fallback.
- `bonusFor(StatKey stat)` — returns the bonus value for a given stat (0
  when the enhancement does not modify that stat). This is a helper used by
  the seam accessors.
- `toAttachedBonus(StatKey stat, Expiry expiry, int createdRound)` — the
  exact grant the engine will make once wired: an ATTACHED-scope StatBonus
  sourced by this enhancement and aimed at the recorded target. Returns null
  when no explicit target is recorded (engine keeps its legacy self-target
  path). Documents the key registry fact: ATTACHED bonuses are read from
  the target owner's registry, so an opponent-targeted penalty must be
  granted INTO the opponent's Player registry and removed there
  (`Player.removeBonusesBySource`).

### Player.java

Added one read-only method:

- `hasAttachedBonusFrom(sourceCardId, targetCardId)` — does any ATTACHED
  bonus in this registry carry the given source card id and target card id?
  Used by the opponent-targeted enhancement wiring to verify a Censure-class
  penalty actually landed on the intended enemy fleet. No mutation, no
  behavior change.

## Verification

- **compile.bat green** — 57 source files, `-source 6 -target 6`, JDK
  1.8.0_292, 1 expected bootstrap warning.
- **Java 6 grep clean** — no lambdas, method refs, streams, diamond
  operators, try-with-resources, or modern syntax in the touched files.
- **No behavior change** — the seam adds fields and accessors only; no
  engine code reads them yet, so existing game behavior is identical.

## Reusable lesson

A model-side data seam (fields + accessors that the engine doesn't yet
reference) compiles green and adds zero behavioral risk — it is safe to
stage as an isolated slice ahead of the engine-wiring task (B5-0469).
The seam's documentation should capture the registry fact the wiring
task will depend on (here: ATTACHED bonuses are read from the target
owner's registry, not the source owner's).
