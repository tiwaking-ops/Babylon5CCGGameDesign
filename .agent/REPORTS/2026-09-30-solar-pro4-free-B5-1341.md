# B5-1341 — CharacterCard reachability into applyGenericCardPlay (2026-09-30)

Do NOT re-audit the B5-1109 UI guards themselves.

## Method
Grep-driven census of `applyGenericCardPlay` call sites, `PLAY_CARD` dispatch, `GameAction.playCard` factory usage, and every caller that can construct a `PLAY_CARD` action carrying a `CharacterCard`. Cross-referenced against `AIPlayer.buildLegalActions`, `MainWindow.playOnly`/`updatePlayInitiateButtons`, `HeadlessHumanSeatProbe.chooseHumanAction`, and `HeadlessConformanceTest` PLAY_CARD test sections.

## applyGenericCardPlay — what it does with a CharacterCard

`GameController.applyGenericCardPlay` (line 630) charges `card.getCost()` raw (line 636), then handles `EnhancementCard`, `LocationCard`, `GroupCard`, `AgendaCard` (with sponsor check), `EventCard`, `ContingencyCard`. A `CharacterCard` matches NONE of these branches: it is removed from hand (line 651), logged (line 652), and **receives no effect**. This is the corruption B5-1109 named. It remains live in the tree as of this census.

## Path census

### Path 1: AIPlayer.buildLegalActions → PLAY_CARD → applyGenericCardPlay

**Status: CLOSED.**

`AIPlayer.buildLegalActions` (line 175) iterates the hand and classifies each card:
- `CharacterCard` (line 191): offered via `GameAction.recruitCharacter(c)`, gated on `canRecruit`. NOT `playCard`.
- The `else` branch (line 214) catches `EnhancementCard`, `LocationCard`, `GroupCard`, `FleetCard`, `EventCard` — offered via `GameAction.playCard(c)`.

CharacterCard is explicitly excluded from the `playCard` offer path on the AI side. An AI can never dispatch a CharacterCard to `applyGenericCardPlay`.

### Path 2: MainWindow (human UI) → PLAY_CARD → applyGenericCardPlay

**Status: CLOSED (two independent guards).**

`MainWindow.playOnly()` (line 2141, the "Play Card" button dispatch):
- Line 2147-2148: `if (selectedCard == null || selectedCard instanceof ConflictCard || selectedCard instanceof CharacterCard) return;` — B5-1171 guard, refuses CharacterCard before any action is submitted.

`MainWindow.updatePlayInitiateButtons()` (line 2117, button enablement):
- Line 2130-2134: `canPlay` requires `selectedCard instanceof CharacterCard` to be FALSE (line 2130), AND `rules.canPlayCard(humanPlayer(), selectedCard)` (line 2134). This is a **production caller of canPlayCard** in MainWindow — B5-1109's claim of "ZERO production callers in MainWindow" is now stale; this line landed with B5-1177.

Both guards must be bypassed for a human to dispatch a CharacterCard to `applyGenericCardPlay`. The UI path is closed.

### Path 3: HeadlessHumanSeatProbe → PLAY_CARD → applyGenericCardPlay

**Status: CLOSED (test harness, gated on canPlayCard).**

`HeadlessHumanSeatProbe.chooseHumanAction` (line 320) classifies the hand:

- `else` branch (line 343): `if (rules.canPlayCard(human, c)) return GameAction.playCard(c)`.

This probe is a **test harness**, not production code. It calls `canPlayCard` before dispatching. If a CharacterCard were in the hand, `canPlayCard` would be consulted; the probe does NOT add a CharacterCard to the hand in any PLAY_CARD test. The harness path is gated and does not reach `applyGenericCardPlay` with a CharacterCard in any existing test.

### Path 4: HeadlessConformanceTest → PLAY_CARD → applyGenericCardPlay

**Status: CLOSED (no CharacterCard in any PLAY_CARD test).**

`HeadlessConformanceTest` PLAY_CARD tests:

No `GameAction.playCard` call in `HeadlessConformanceTest` carries a `CharacterCard`. The conformance suite does not reach `applyGenericCardPlay` with a CharacterCard.

### Path 5: HeadlessSmokeTest / HeadlessMultiRoundTest → PLAY_CARD → applyGenericCardPlay

**Status: CLOSED (AI-only players, no human dispatch).**

Both harnesses drive AIPlayer exclusively. AIPlayer does not offer CharacterCard via `playCard` (Path 1 closed). Neither harness constructs a `GameAction.playCard` with a CharacterCard. No reachable path.

It does NOT open a CharacterCard path (the `instanceof CharacterCard` guard at line 2130 still excludes it), but it does mean `canPlayCard` is now consulted in production MainWindow code.
