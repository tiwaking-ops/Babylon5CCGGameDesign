# B5-0451 — Conflict-initiation targeting audit (B5-0328/B5-0442 follow-up)

## Surface audited (all read-only)

* `MainWindow.updatePlayInitiateButtons()` — b5ccg/src/b5ccg/ui/MainWindow.java:1507–1541
* `MainWindow.initiateOnly()` — MainWindow.java:1549–1569 (fallback at :1554–1563)
* `MainWindow.applyCardSelection()` — MainWindow.java:1575–1628 (target population :1582–1596)
* target selector listener — MainWindow.java:441–455
* `MainWindow.clearSelection()` — MainWindow.java:1619+
* Engine gate: `RulesEngine.canInitiateConflict(p, c, target, state)` — RulesEngine.java:642–661
* AI counterpart: `AIPlayer.leadingPlayer` — AIPlayer.java:128+

## Findings (ranked)

### F1 — MEDIUM-HIGH: selector population auto-picks a target, defeating the explicit-choice gate

`applyCardSelection` (hand conflict path, :1582–1596) calls
`targetSelector.removeAllItems()` then `addItem(...)` per non-human player.
A JComboBox auto-selects the first added item and fires its
`actionPerformed`, so the listener at :441–455 sets `selectedTarget` to the
FIRST non-human player without any user action. Consequences:

* The status label says "Target: choose from dropdown" but a target is
  already chosen programmatically.
* The B5-0325 F2 `targetReady` gate (:1523–1524, "require an explicit
  target so Initiate can't fire on a stale auto-fallback") is satisfied by
  this auto-pick — `initiateConflictButton` lights immediately, and a click
  submits with a target the user never picked (still engine-legal: the
  gate validates legality, not intent).

This is the same population-fires-event class captured in the pattern
`map-ui-choice-selectors-to-live-objects` (opencode). Fix shape for the
fix slice: suppress the listener during population (guard flag or listener
swap), leave `selectedTarget` null until a real change event, mirroring the
B5-0440 attack selector's placeholder-then-explicit pattern.

### F2 — MEDIUM: stale target carries across card selections

`applyCardSelection` never resets `selectedTarget` when the selection
changes card (only `clearSelection` does, :1620). A target picked while
conflict A was selected silently satisfies `targetReady` for conflict B;
combined with F1 the highlighted dropdown item may not even correspond to
the carried `selectedTarget` object. Fix shape: reset `selectedTarget` +
selector selection inside `applyCardSelection` whenever `card` changes.

### F3 — LOW: the initiateOnly highest-influence fallback is dead code in practice

The fallback (:1554–1563) is unreachable under the current enablement gate:
the button can only fire when `targetReady` is true, and with
`conflictSelected` the selector is always enabled (board selections never
present ConflictCards, B5-0423), so `targetReady` is false exactly when
`selectedTarget == null` — the only condition the fallback covers. This
sharpens B5-0442's "out of scope" note into a reachability verdict. It does
NOT duplicate the AI's `leadingPlayer` scoring: different metric (raw
influence vs type-scoped conflictTotal) and different caller; with the
fallback dead there is no live duplication. Recommend deleting the block in
the 0452 fix slice to remove the misleading path.

### F4 — LOW (pre-existing, deferred by B5-0328): phase gate breadth

`phaseAllowsAction` (:1516–1518) permits initiation during
CONFLICT_RESOLUTION/AFTERMATH/DRAW. Rulebook-faithfulness of non-ACTION
initiation remains an open interpretation; unchanged since B5-0328's
deferred note.

### F5 — INFO: no illegal submissions possible

The engine validates every submission (`canInitiateConflict` is wired in
GameController's INITIATE_CONFLICT branch, B5-0302), so F1/F2 can produce
an unwanted-but-legal target, never an illegal action. Worst case is
intent damage, not state corruption.

## Verdict for the fix-slice gate

Defects reported; F1 is the highest-severity finding and seeds B5-0452's
scope (ui/-only listener-guard + explicit-selection fix; F2 rides along;
F3 optional cleanup). NO code edits made in this audit.

## Reusable lesson

Populating a JComboBox is not a neutral act: auto-selection fires the same
listener a user click would, so any "explicit choice required" gate built
on selection state must guard the population window, or the gate is
satisfied by the widget itself.
