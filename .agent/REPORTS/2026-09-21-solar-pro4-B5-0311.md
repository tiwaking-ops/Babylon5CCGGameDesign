## 3. Finding C1 (P0/HIGH) — No card in either file carries a `cost` field

**Criterion:** missing cost field per D13 (B5-0203 audit finding).

**Observation:** I checked every card object in both files for a `cost`
key. None has one. The only numeric fields per card type are the ability
stats and, for conflicts, `influenceReward`; for locations,
`influencePerRound`; for agendas, `isMajorAgenda` + `winCondition`; for
aftermaths, `triggerCondition`. There is no `cost` key on characters,
fleets, locations, enhancements, events, agendas, conflicts, groups, or
aftermaths in either file.

**Why it matters:** B5-0203 D13 recorded that the model does not carry a
card cost field, and B5-0305's D13 note explicitly says the double-cost
rule "needs a card cost field the model does not carry." If the project
ever implements the rulebook's double-cost rule (loyal other-race
characters cost double; restricted race-named cards are unplayable to
other races), the data needs a source of truth for printed cost. Today
the model infers/ignores cost because the engine does not apply it, but
the data has no field to hold it when/if that changes.

**Scope of the gap:** both files, all card types. This is a data-schema
gap, not a typo — it affects every card uniformly.

**Rulebook reference:** B5-0203 D13 note; rulebook §IV "Character Cards"
/ §V "ACTION: Sponsor a Supporting Card" (loyal other-race double cost);
§V "ACTION: Promote a Character to the Inner Circle" (promote cost =
sponsor cost + 1 per Inner Circle member); §IV "Anatomy of a Card" item 2
(Influence Cost is a primary card attribute).

**Proposals (report-only; no JSON edit made):**

- P1 — if the project intends to implement double-cost / restricted-card
  playability on the data side, add a numeric `cost` field to character,
  fleet, location, enhancement, event, group, and conflict objects
  (aftermaths may not need it; their "cost" is the conflict's existence
  and their play condition, not an influence payment). Start with
  characters and fleets (the types the double-cost rule actually touches),
  and backfill from rulebook card text / existing printed-card reference
  where available. Record that B5 IP-safe rules forbid copying card text,
  so cost values would need to come from a source the project is allowed
  to use.
- P2 — if cost stays model/inferred-only for now, add a schema note
  (e.g. in `docs/` or a `cards/README`) that `cost` is intentionally
  absent and record why, so a future auditor does not flag the same
  absence as an unexplained omission.

## 4b. Observation P5 (P3/LOW) — no `PSI_PARTICIPANT` condition in the data

The data uses `WON_DIPLOMACY`/`LOST_DIPLOMACY`,
`WON_INTRIGUE`/`LOST_INTRIGUE`, and
`MILITARY_PARTICIPANT`/`INTRIGUE_PARTICIPANT`/`DIPLOMACY_PARTICIPANT`.
There is **no** `PSI_PARTICIPANT` token in either file, and no aftermath
targets "participated in a Psi conflict" specifically. That is consistent
with the data set (no Psi-participant aftermath exists), not a schema
error — but if a future card wants "play after participating in a Psi
conflict," the vocabulary would need a `PSI_PARTICIPANT` value and the
engine would need to recognize it. I am recording this as a vocabulary
completeness note, not a defect, because the data simply has no such card.

## 5. Finding C3 (P2/MEDIUM) — No shared card-id namespace guard across the two files

**Criterion:** id/text match (and, by extension, id uniqueness).

**Observation:** within `premiere.json`, every `id` I sampled is unique
(e.g. `char_jeffrey_sinclair`, `fleet_homeworld_human`, `agenda_revenge`,
`conf_blockade`, `enh_mass_drivers`, `event_underworld_connections`,
`aftermath_war_hero`, `group_observers`). Within `deluxe.json`, the ids
use a `de_` prefix for the same logical card where a premiere counterpart
exists (e.g. `de_char_adira_tyree` vs `char_adira_tyree`), and the
non-prefixed ids in deluxe are unique within deluxe. The two files
therefore use **different id prefixes for the shared-card overlap**
(`de_` vs none), which avoids collision for the premium counterpart
cards.

What the data does **not** have: any cross-file uniqueness invariant, no
id prefix convention documented in the repo, and no manifest that maps
id → set. A future third set (e.g. an expansion JSON) could collide with
a premiere id if the author does not know the convention.

**Text consistency (spot-checked, not exhaustive):** for the cards I read
in full, `title` is a human-readable name and `text` is the card-text
field; they are consistent with each other and with the id's implication
(e.g. `char_jeffrey_sinclair` / "Jeffrey Sinclair"). I did not find an
id/title mismatch in the cards I read; I did not exhaustively diff all
448 premiere ids against titles because the task is report-only and the
id/text match criterion is about structural consistency, which looks fine
at the level I inspected.

**Why C3 is P2 not P1:** there is no actual collision in the current two
files, and the `de_` convention already avoids it for the overlap cards.
This is a governance/convention gap, not an active bug.

**Proposals (report-only; no file edit made):**

- P6 — add a short `cards/README` (or a `docs/` note) stating: card ids
  are globally unique across all `cards/*.json`; premiere uses bare ids,
  deluxe uses `de_` prefix for counterpart cards; new sets should pick a
  distinct prefix and avoid the premiere/deluxe id space. This is a
  low-effort, high-value record for future data authors.
- P7 — optionally add a one-line manifest (`cards/index.json` or similar)
  listing each file's set name and card count, so a future auditor can
  verify counts without parsing both files by hand. Purely administrative;
  not required for correctness.

## 6. Finding C4 (P3/LOW) — No card-level set membership metadata beyond the `set` string

**Criterion:** schema consistency (general).

**Observation:** every card has a `"set":"PREMIERE"` or `"set":"DELUXE"`
string. That is the only per-card set marker. There is no card-level
rarity distribution summary, no card-number/collector-number field, no
artist field, no reprint flag, and no per-file header object. This is
fine for the engine's current needs (deck loading only needs id, title,
type, stats, faction, text, rarity, imageKey, and type-specific fields),
but it means the `cards/` directory is a raw card dump rather than a
self-describing data set. Not a defect; a completeness note.

**Proposals (report-only):**

- P8 — if the project ever wants per-card collector numbers or set
  metadata, add them as optional fields and document the schema. Low
  priority; record only.

## 6. What is NOT a defect (by design / acceptable)

- **No `cost` field today is consistent with the current engine,** which
  does not apply a printed cost (B5-0203 D13 + B5-0305 note). C1 is a
  "future-proofing / schema gap" finding, not a data error relative to
  the code as it stands.
- **`deluxe.json` reuses premiere text with deluxe variants.** Several
  deluxe cards have parenthetical deluxe-only clarifications in their
  `text` (e.g. Adira Tyree's "Deluxe: may target any opponent..."). That
  is a reasonable data convention for a deluxe add-on set; not a
  consistency problem.
- **Aftermath condition names are engine-aligned in the current data.** The
  corrected `triggerCondition` census (C2 retraction) shows every value in
  the data is in the engine-recognized set; `aftermath_disgrace`'s
  `LOST_MILITARY` matches both the engine and its own text. No data typo
  exists.
