### 1. Parses — PASS

`bash -n b5ccg/compile.sh` exits 0. Toolchain caveat: `bash` is **not on PATH**
on this host. A bare `bash -n` returns exit 1 with
`execvpe(/bin/bash) failed: No such file or directory` — that is a
**WSL-not-installed error, not a syntax verdict**, and reading it as a parse
failure would have filed a false defect against a correct file. The real shell
is Git Bash at `C:\Program Files\Git\bin\bash.exe`, which must be invoked by
full path. This is the loop doc's "absence of an error is not presence of a
value" trap.

### 3. `set -e` abort semantics — CONFIRMED

The comment asserts that `set -e` above aborts on the first non-zero exit, so
each gate's code is honoured without extra plumbing. Proven, not assumed: a

The claim holds as written.

### 4. CRLF warning — does NOT matter here, and the reason is measured

`git diff` prints `LF will be replaced by CRLF the next time Git touches it`,
and `core.autocrlf` is `true` with **no `.gitattributes`** in the repo. That
looks alarming for a shell script, so it was tested rather than argued:

- The **committed index** blob is LF and so is the **working copy** right now —
  `git ls-files --eol` reports `i/lf w/lf`, and `od -c` on line 1 shows
  `#!/bin/bash\n` with no `\r`. The warning is about a *future* checkout, not
  about the bytes on disk.
- A **synthesised CRLF copy**, executed in place under Git Bash, builds
  successfully: `CRLF_EXIT=0`, 63 sources compiled, `✓ Build successful`.
- The same CRLF copy invoked as `bash <file>` also succeeds: `CRLF_BASH_EXIT=0`.

Git Bash tolerates a trailing `\r` on the shebang. So under the shell this repo
actually uses, the CRLF conversion is **cosmetic**.

**The caveat that keeps this from being a blanket green:** the repo's own header
comment on `compile.sh` records that "CRLF line endings additionally broke
stricter shells" (B5-0306). Git Bash is not a stricter shell — `dash` and some
`sh` builds are. The mitigation is already in place and is why this is not a
defect: the script works from **relative paths** resolved via
`cd "$(dirname "$0")"`, so it does not depend on MSYS path translation. A
`.gitattributes` marking `b5ccg/compile.sh` as `text eol=lf` would remove the
warning permanently, but that is a **new file outside my claimed scope**, so it
is recorded as a recommendation and not made.

### 5. Gate green end to end — PASS

`RUN_TESTS=1 ./compile.sh` completed with **`SCRIPT_EXIT=0`**. The 880-line log
shows the build (`✓ Build successful`), the two pre-existing suites
(`HeadlessConformanceTest`, `HeadlessSmokeTest`), all seven new gates running in
the file's order, and the closing `✓ Verification passed.` The last gate to emit
was `HeadlessWarConflictProbe` → `B5-0419 PROBE PASSED (all DECLARE_WAR_CONFLICT
scenarios)`, which is the seventh of seven, so the whole added block executed
rather than being skipped.

**Build environment note:** the run takes well over the 30s command window, so
it was launched detached and polled on a file-written exit marker. Capturing the
exit code inline through PowerShell silently fails — PowerShell eats the `$?`
before bash sees it, and the run appears to hang forever. Write the exit code to
a file from inside the bash script, then read the file.

**Reusable lesson:** a green-looking shell failure can be a missing interpreter
rather than a bad script — `bash -n` returning exit 1 with
`execvpe(/bin/bash) failed` is WSL-missing, not syntax-invalid, and on this host
Git Bash must be called by full path; and for a repo-wide `core.autocrlf=true`
with no `.gitattributes`, measure the CRLF question on a synthesised copy under
the shell you actually use instead of reasoning from the warning text, because
Git Bash tolerates `\r` on a shebang while stricter `sh` builds do not.
