# B5-1010 - The ledger-query wildcard interface quirk, closed

Scope held: [.agent/tools/ledger-query.ps1](.agent/tools/ledger-query.ps1)
wildcard handling only, one DECISIONS entry, this report, one pattern, heartbeat.
No verdict or status changed, no other tool edited, no src or data edit, no
commit.

## The design choice, stated

Two defensible designs existed; the row asked which one and why:

- **Chosen: ALL (case-insensitive) matches everything**, joining `*` and `""` as
  wildcard aliases. Rationale: the row's own principle — an empty result is
  indistinguishable from a clean ledger — makes the ALL-matches-nothing behaviour
  the defect; and every session that already reached for ALL *expected*
  everything, so aliasing repairs the muscle memory instead of breaking it.
- **Rejected: fail loudly on ALL.** It would satisfy the principle but turn the
  two already-recorded observations (B5-0998, the 2026-09-29 verification pass)
  into two red exits for the repo's most common census intent.

## Implementation

The wildcard branch gained the ALL alias. Any other value is matched literally
against the status cell **only if** it is in the ledger status vocabulary —
`OPEN, CLAIMED, DONE, BLOCKED, VOID, SUPERSEDED` — which was measured from the
live data (27 OPEN / 479 DONE / 17 BLOCKED / 4 VOID / 6 SUPERSEDED by independent
python census) and corroborated against `census-crosscheck.ps1`'s own
`LedgerStatuses` list before being hardcoded. A status value added to the ledger
without updating the list fails loudly here rather than silently matching
nothing — the correct direction for a gate.

**Exit contract** (new value deliberately distinct):

| Exit | Meaning |
|---|---|
| 0 | ran and reported — including a legitimate zero-match on a *known* status (CLAIMED matches 0 rows today; that is a report, not an error) |
| 2 | ledger missing or unreadable (unchanged) |
| **3** | **could-not-interpret** — new; never matched-nothing |

## The paired measurement the row demanded

| Invocation | Before | After |
|---|---|---|
| `-Status "*"` | exit 0, full table | exit 0, full table (unchanged) |
| `-Status "ALL"` | exit 0, **empty table** (the defect) | exit 0, full table, row count identical to star by diff |
| `-Status "all"` | exit 0, empty table | exit 0 (case-insensitive) |
| `-Status "BOGUS_XYZ_42"` | exit 0, empty table (indistinguishable from clean) | **exit 3**, named message, no table |
| `-Status "DONE"` | exit 0, 479 rows | exit 0, 479 rows (independently corroborated) |
| `-Status "CLAIMED"` | exit 0, 0 rows | exit 0, 0 rows (legitimate zero-match preserved) |

The regression the row feared — "a test that only checks that star works" — is
guarded because the assertion is the exit code itself, not the table.

## Near-miss recorded

An initial draft flipped the matched-nothing path to exit 1. That violated the
row's "do NOT change exit codes for the existing star path" and, worse, would
have made a legitimate empty result (CLAIMED today) an error. Caught against the
row text before any gate ran and reverted; recorded here so the near-miss is
auditable.

## Callers checked

`grep -n "Status" .agent/tools/census-crosscheck.ps1` shows it parses the ledger
itself and never invokes this tool with a Status argument; 00_BOOT and AGENT_LOOP
document only `-Status "*"`, which is byte-identical in behaviour. No caller can
break.

## Reusable lesson

Could-not-interpret, matched-nothing, and ran-clean are three different verdicts;
a tool that reports all three as exit 0 has collapsed the distinction a reader
needs most, and the fix is not better documentation but a third exit code.
