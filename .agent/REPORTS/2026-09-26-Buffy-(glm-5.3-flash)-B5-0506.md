# B5-0506 — First near-class wiring slice (B5-0497 slice 1: shunned pair)

Task: wire the top-ranked near-class opponent-mentioning enhancement pair
through the 0468 seam + 0473 CardEffects path with its distinct
consumption-path difference preserved; conformance section; engine + suite
only. Claimed 05:09:24Z after the previous claimant released the row without
closing it; B5-0497's ranking table (both 0497 reports) ranks
`enh_shunned`/`de_enh_shunned` #1 (LOW cost): CHARACTER host + multi-stat
penalty + reactive discard-on-heal.

## 1. Implementation (3 engine files, no model/data edits)

* **CardEffects.java** — (a) `DISCARD_ON_HEAL` id registry (`enh_shunned`,
  `de_enh_shunned`) + `discardsOnHeal(String)` gate; (b) `characterById`
  helper (face-up lookup across IC, Supporting Role, ambassador — mirrors
  `fleetById`); (c) new explicit-target branch in the
  `ENHANCEMENT_CHARACTER` path of `applyPlayEnhancement`: attaches to the
  CHOSEN opponent character, grants the four per-stat penalties INTO the
  victim's registry (ATTACHED scope keyed to their character id, read back
  through `owner.effectiveStat` — the distinct consumption-path difference
  vs Censure is CHARACTER host + multi-stat + reactive discard), holds the
  card with no registry effect when the target cannot be resolved (no
  self-fallback, B5-0473 rule). Untargeted character enhancements keep the
  legacy self path byte-identically.
* **RulesEngine.java** — reactive hook at the single heal site
  (`executeHealCharacter`): after a successful heal, the discard-on-heal
  enhancement attached to the healed character is discarded from WHOEVER
  holds it (its playing player — typically the opponent) and its granted
  bonuses are lifted from ALL player registries (they land in the victim's,
  not the holder's). Matching is by `targetCardId == healed character id`,
  so other held discard-on-heal cards are untouched.
* **HeadlessConformanceTest.java** — new SHN section, 16 checks (444→460),
  wired into main() next to ENH-WIRE.

## 2. Defects found and fixed during verification (test-driven)

1. **Fixture id mismatch (my test bug, engine right):** first run failed 4
   checks because the fixture used id `enh_shunned_w1` while the discard
   registry (correctly) keys on the real pool ids — the end-to-end path
   under test IS the pool-id path. Fixed the fixture to use `enh_shunned` /
   `de_enh_shunned` (the "unresolvable target" fixture reuses the deluxe id).
2. **Lift scope (real engine bug, caught by the suite):** the hook first
   lifted bonuses only from the holder's registry, but the penalty lands in
   the VICTIM's registry (the 0468/0473 seam the slice consumes). Fixed to
   sweep all registries on discard. This is exactly the cross-registry
   asymmetry the 0497 report flagged as the pair's distinct consumption path.

## 3. Data note (observation, no edit)

Both shunned records carry `militaryBonus: 0` while the printed text says
"loses 2 from all stats" — the same text-vs-data class B5-0311 recorded.
Per the data-wins rule the implementation applies the four data fields as-is
and the conformance fixture mirrors the DATA (Military delta 0), noting the
discrepancy. A data pass could later set militaryBonus to -2; the engine
needs no change for that (the grant is per-stat).

## Reusable lesson

When a reactive effect's card leaves ONE player's possession but its
registry footprint lives in ANOTHER's (the 0468 seam's whole point), the
removal path must sweep every registry, not the holder's — write the
conformance check for the registry the bonus actually landed in, or the
suite will catch the asymmetry the way this one did.
