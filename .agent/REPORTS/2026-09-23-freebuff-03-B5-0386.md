## Rulebook ground truth for the future E2 implementer

* :733-735 — the mechanic: cards "used each turn only by the player who
  applies the most influence to control them"; bids are **cumulative** across
  the turn; mercenaries act **after all players pass, before the Resolution
  round**; the highest cumulative bidder dictates the mercenary's action.
* Maps to B5-0360 §3.2 E2 contracts verbatim (bid state, BID_ON_MERCENARY,
  MERCENARY phase before CONFLICT_RESOLUTION, tie-break open question).
* The mechanic is defined purely by card text; the rulebook names no specific
  cards in the excerpt, consistent with a Great War-era card pool we do not
  have.

## Flag schema recommendation: boolean field, NOT subtype overload

**Recommended:** optional `"mercenary": true` boolean on the card record,
absent = not a mercenary (backward-compatible: loader hydrates default false,
exactly the B5-0335 `cost` / B5-0336 `participation`/`fleetClass` precedent
of additive optional fields).

**Rejected — subtype overloading.** Evidence from the live census: `subtype`
is the project's single-value faction/race/trigger channel
(CHARACTER_HUMAN ×35, FLEET_NARN ×18, AFTERMATH_LOST ×33, CONFLICT_DIPLOMACY
×47, …). A MERCENARY value there would (a) erase faction/race information on
the cards that carry it (single string field), (b) collide with every
consumer that reads subtype as faction (Faction.isPlayableBy-style parsing,
B5-0336's fleetSubtypes/participation gating), and (c) have no SNRPG decode
counterpart to verify against. B5-0353/B5-0387 reached the same conclusion
for fleets: class-like data gets its own field, not the faction channel.

**Future upgrade path:** if a real mercenary card ever needs parameters
(bid floor, per-turn usage count, faction restrictions), migrate the boolean
to a nested object under the same key — the loader hydration seam is
identical, and no engine code reads the field until E2 lands.
