# B5-1035 — encoding receipt robust to being consumed

Reusable lesson (one line): a verdict token must stay at fixed column 0 (line 1) and the receipt must be on its own line (line 3), so both `line-contains-PASS` and `line-starts-with-PASS` work; never embed receipt in the verdict parenthetical.

Scope (per row): `.agent/tools/run-dup-census.ps1` only. No `b5ccg/src/` edited, no exit code / verdict word / count changed.

Finding: `run-dup-census.ps1` previously emitted `PASS (0 duplicate) [encoding: UTF-8 (explicit)]` — PASS embedded in parenthetical with receipt, breaks fixed-position parsing.

Fix (chosen over alternatives): put verdict on its own line at col 0 (`PASS` / `FAIL`), receipt on separate line 3 (`-- ENCODING: UTF-8 (explicit) --`). Alternative (fixed position within line) would require every consumer to know column offsets; separate lines keep `line-contains` and `line-starts-with` both working with zero change to consumer code.

Proof:
- Verdict token extractable by `line-starts-with`: yes (line 1).
- Verdict token extractable by `line-contains-PASS`: yes (token still present).
- Exit contract preserved: 0 = PASS, 1 = FAIL (line 64-65 edit, no branch changes).
- `ledger-query.ps1` ENCODING footer untouched (line 371-375, not in scope).
- No new external library; Java 6 / stdlib not touched (not a build task).
