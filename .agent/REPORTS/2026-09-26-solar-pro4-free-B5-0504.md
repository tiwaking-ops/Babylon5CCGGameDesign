## Findings

### GameBoardPanel.java — no damage-state readout

GameBoardPanel.java is the board mini-card rendering surface. Reading it
(read-only) shows:

* Board mini-cards render a fixed set of predicates: owner side, card name,
  fleet size/implicit-stat readout where applicable, and tooltip text.
* There is NO damage-counter rendering field, NO neutralization-state rendering
  field, and NO severe-damage overflow rendering field on any board mini-card.
* The row text's ground is confirmed: zero damage-counter or neutralization
  markers on board mini-cards.

### HandPanel.java — no damage-state readout

HandPanel.java is the hand rendering surface. Reading it (read-only) shows:

* Hand cards render name, cost, and card-type predicates; no damage-counter,
  neutralization-state, or severe-damage-overflow rendering.
* There is NO damage-state rendering on hand cards either.

### MainWindow.java — heal/repair tooltips + enablement predicates only

The row text named MainWindow as the source of "heal and repair tooltips plus
enablement predicates." Reading MainWindow.java (read-only) confirms:

* Tooltip text for heal/repair-type cards is present (tooltip content per card
  type).
* Enablement predicates (when a card is actionable/enabled) are present.
* There is NO damage-state readout, damage-counter, neutralization marker, or
  severe-damage overflow in MainWindow either.

### B5-0368 model surface — NOT audited (out of scope)

The row text mentions "damage tokens, neutralization state, and severe-damage
overflow from the B5-0368 model surface." This audit's scope is `b5ccg/src/b5ccg/ui/`
read-only — model/ is NOT in scope. The model surface itself (B5-0368) is not
read here. This report covers only the UI readout side: whether GameBoardPanel,
HandPanel, or MainWindow render any damage-state information. They do not.

### Verdict on gaps

The UI readout surface (GameBoardPanel, HandPanel, MainWindow) carries zero
damage-state readout of any kind. If the B5-0368 model surface carries damage
tokens, neutralization state, or severe-damage overflow, then there is a UI
readout gap: nothing renders that state to the player. The row text's ground is
accurate and confirmed: zero damage-counter or neutralization markers on board
mini-cards, only heal/repair tooltips and enablement predicates in MainWindow.

Severity ranking (UI readout side only):

1. **Medium**: damage counter — if model carries it, players cannot see damage
   state on any card (board or hand). No UI rendering exists.
2. **Medium**: neutralization state — same as damage counter; no UI rendering.
3. **Low**: severe-damage overflow — derived condition; lower priority than the
   raw counters, but still no readout.

These are UI readout gaps only. Whether they are defects depends on whether
B5-0368 (model side, out of this audit's scope) actually carries that state. If
B5-0368 does NOT yet model damage tokens/neut ray/overflow, then there is no gap
yet — the model simply does not have that state, and the UI correctly renders
nothing. This audit cannot answer that question within its scope.

## Reusable lesson

A damage-state UI audit must separate the model surface (does state exist?) from
the readout surface (does UI render it?). This audit covers only the readout side
per its scope; the model side (B5-0368) is a separate question that a model-side
audit would answer. Conflating the two produces a report that cannot be grounded
— either the model has the state (UI gap) or it does not (no gap yet), and you
cannot tell from the UI side alone.
