# B5-2379 — Re-verify selection-driven button enablement after the toolbar fix

Gate B5-2375 DONE verified on the row before claiming. Scope: ui/ only,
Java 6, `compile.bat` green, no commit.

## 1. The finding: selecting a card never lit Sponsor or Promote

Measured live with a scratch headless probe (git-ignored `b5ccg/out/scratch`,
deleted after the run): a real game driven to a human ACTION window, a real
`MainWindow` constructed off screen, a real `applyCardSelection` call on an
affordable in-hand character. Every Sponsor conjunct true — ACTION phase,
my turn, correct selection, face-up, unrotated, in hand,
`rules.canRecruit` true — and `sponsorButton.isEnabled()` **false**.

Root cause: Sponsor / Promote / Build Influence enablement was derived in
`refresh()` only (then MainWindow.java:2006-2038). Selecting a card runs
`applyCardSelection()`, which re-derived only Play / Initiate (via
`updatePlayInitiateButtons`) — so Sponsor and Promote stayed however the
last engine refresh left them until the next state change. In live play AI
actions stream refreshes constantly, which masked it; in a quiet human turn
the player sees a dark Sponsor on a sponsorable character. Pre-existing, not
a toolbar-fix regression (committed HEAD has the same shape) — but this
row's premise ("selecting lights exactly the legal actions") was never true
for Sponsor/Promote, so the row owned the repair.

## 2. The fix (ui/MainWindow.java only, +50/-28)

Extracted the three gates verbatim into one authority,
`refreshSponsorPromoteBuildInfluence(human, ch, actionPhase, myTurn)`,
called from three places:

- `refresh()` — same call, same arguments, behaviour-identical;
- `applyCardSelection()` — on every hand/board/picker selection (all three
  real click paths funnel through it: :789, :1352, :1363);
- `clearSelection()` — after a submit, so a spent selection goes dark at
  once instead of lingering lit.

No predicate changed: the conjunctions are byte-identical, only the call
sites are new. The method name matches the existing convention where
enablement lives in a named authority (`updatePlayInitiateButtons` precedent).

## Reusable lesson

A button that is correct on every refresh can still be wrong on every click:
enablement derived only on state-change events is blind to selection-change
events, and a busy game masks the gap by refreshing constantly — so the
failing case is the quiet human turn, which is exactly the case no suite
exercised until a probe selected a card and read the button instead of the
predicate.
