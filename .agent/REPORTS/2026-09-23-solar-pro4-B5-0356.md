# B5-0356 — SNRPG row-filter definition

## Scope

Report-only. Defines which Saturday Night RPG (saturdaynightrpg.co.uk) B5CCG
table rows map to our 446-title-deduped card pool, via a composite-key rule.
No pulls, no JSON edits, no src/ edits. Grounds any future data task that
wants to use SNRPG as a source.

## Pool definition (authoritative)

Our pool = 446 unique titles, defined by B5-0320's title-dedup rule:
- 383 DELUXE (deluxe.json, set=DELUXE)
- 63 premiere-only (premiere.json cards with no deluxe counterpart; title-dedup
  keeps premiere copy when no deluxe twin exists)
- Tie-break: deluxe wins when both sets carry the same title.

Title is the dedup key. ImageKey agrees 100% on the overlap (verified per
B5-0320). Our cards carry their own `id` field (e.g. `char_jeffrey_sinclair`),
which is independent of SNRPG's `KeyID`.

Pool composition (post B5-0335 cost backfill):
- premiere.json: 446 records, 209 with cost
- deluxe.json: 383 records, 168 with cost
- 452 cards remain without cost (null preserved)

## Composite key

The matching key for "does this SNRPG row represent a card in our pool" is:

    (title_normalized, SNRPG_Set_code, SNRPG_Type_code)

with KeyID retained as a cross-reference column in any output (NOT used as our
card id).

### title_normalized

Lowercase, strip all non-alpha characters (spaces, hyphens, punctuation,
edition markers like "Deluxe", "Promo", "Fixed"), then match against our
title-lower set.

Examples (B5-0335 precedent):
- "Jeffrey Sinclair" → "jeffreysinclair"
- "Level the Playing Field 3+9" → "leveltheplayingfield" (note: SNRPG has
  "Level the Playing Field" without the "3+9" suffix; our premiere.json uses
  the longer title — title match still succeeds because normalization strips
  the " 3+9" difference)

## Filter rules (which SNRPG rows map to our pool)

A SNRPG row maps to our pool when ALL of the following hold:

1. **Title match**: normalized title matches a title in our 446-title pool.
2. **Type eligibility**: SNRPG Type ∈ {3 (CHARACTER), 6 (ENHANCEMENT), 8 (FLEET),
   10 (LOCATION)} OR Type 9 (GROUP) with a title match to our pool.
   Types 1, 2, 4, 5, 7 are non-sponsorable — skip for cost write (but they
   still "map to our pool" if the title matches; the filter is about data
   eligibility, not pool membership).
3. **Rarity eligibility**: SNRPG Rarity ∈ {1, 2, 3, 4}. Rarity 5/6 → skip.
4. **Set handling**:
   - Set 1 (Premier) or Set 3 (Deluxe): write directly if title matches.
   - Set 2, 5, 7, 8: write if title matches our pool (cross-set reprints
     that exist as deluxe/premiere in our pool). This is how "Psi Corps
     Intelligence" Set 5 matched to our GROUP card in B5-0335.
   - Set 4: write if title matches, mark CAUTIOUS (partial decode).
   - Set 6: verify per-title before write (partial decode; Nightwatch trait
     dominance suggests Psi Corps content, but set name unconfirmed).
   - Set 9: skip (promo singles, not in our 446 pool).
5. **Race handling**: match our faction or Race 6 (no-race) or Race 7 (neutral).
   Race 8/9/10 → skip unless the title is already in our pool by a different
   race mapping (rare; our pool has a few Drakh/Shadow/Vorlon cards via title
   match).

A SNRPG row that passes the title match but fails type/rarity eligibility is
still "in our pool" by title — it just doesn't get a cost write. This
distinction matters for acceptance sampling: a card can be in our pool but
have null cost because it's non-sponsorable or Rarity 5/6.

## Cross-set reprint handling

SNRPG may carry multiple rows for the same title at different Set codes
(e.g. "Psi Corps Intelligence" at Set 1 Rarity 4 and Set 5 Rarity 4 — both
Cost=6, both matching our GROUP card). When this happens:

- The title match succeeds regardless of which Set row is used.
- If our pool has both a premiere and deluxe copy of the title (title-dup
  per B5-0320), the Set code guides which version gets the PRIMARY match
  (Set 1 → premiere, Set 3 → deluxe), but per B5-0335's assumption, cost is
  written to ALL versions of the matched card (both premiere and deluxe
  copies) because both are in the pool and represent the same card.
- KeyID is retained as a cross-reference: each SNRPG row's KeyID is recorded
  alongside the matched our-card id, so a future task can trace which SNRPG
  row contributed which data.

## Edge cases

### Duplicate KeyID pairs (Rarity 6)
11 titles have duplicate KeyIDs in SNRPG (e.g. 195/196, 400/401, 419/420,
733/734, 882/883, 885/886, 1381). These are byte-identical except KeyID and
FlavorText quote — alternate forms (autograph+base, foil+base). NOT in our
pool. Skip (Rarity 6 rule). Do NOT backfill their cost.

### "Kosh Naranek" dual identity
SNRPG has "Kosh Naranek" as Type 3 (CHARACTER, our pool) AND as Type 9
(non-ambassador character, Set 4, Race 7 — NOT in our pool). The two are
different functional cards in the same title family. Title match would match
both to our Kosh Naranek CHARACTER card; the Type-9 row should be skipped
because it's a different card identity. Our pool's char_kosh_naranek is the
ambassador-character version.

### "Quadrant 14" vs "Quadrant 37"
Two distinct DELUXE cards with different titles and different costs (6 vs 10).
Title match resolves them correctly. No ambiguity.

### "Sleeping Z'ha'dum" (Cost=0 from Set 4)
Matched from SNRPG Set 4 → CAUTIOUS flag. Cost=0 written (legitimately free
per SNRPG Cost column, which is an explicit value not a missing bubble per
B5-0334). Title match succeeds despite Set 4 decode uncertainty.

### "Mars Colony" (Cost=6 from Set 4)
Same CAUTIOUS treatment as Sleeping Z'ha'dum. Cost 6 written. Set 4 decode
is partial; the card exists in our deluxe.json with DELUXE set identity,
which is consistent with Set 4 being a Deluxe-era expansion.

## What "maps to our pool" means vs "gets a cost write"

This is the key distinction for any future data task:

- **Pool membership** (title match): 446 titles. A card is IN our pool if its
  normalized title matches one of the 446. This is binary.
- **Data eligibility** (type + rarity + set + race filters): a subset of the
  446. A pool member may be ineligible for a specific data write (e.g.
  AGENDA cards are in our pool but don't get cost writes because they're
  non-sponsorable).

For B5-0335: 210 SNRPG records matched our pool (209 unique titles + 1 dup
for Psi Corps Intelligence). 768 SNRPG records were eligible for cost write
(after type+rarity+set filtering). 377 cost entries were written. 452 pool
cards remain without cost.

## Acceptance criteria for a future pull task using this filter

1. Must use the composite key (title_normalized + SNRPG Set + SNRPG Type) as
   defined above.
2. Must apply the type/rarity/set/race eligibility filters before writing any
   data.
3. Must retain KeyID as a cross-reference column in any output.
4. Must NOT pull without explicit human go-ahead (IP + governance constraint;
   see B5-0311, B5-0334, B5-0355 reports).
5. Must cross-check scan ground truth for text authenticity before writing
   any non-cost field (B5-0355 finding: Adira/Du'Nar game-text divergence
   from premiere.json means bulk text backfill is unsafe until the
   text-authenticity gap is resolved).
6. Must mark CAUTIOUS any match from Set 4/6/8 (unconfirmed set names).
7. Must treat Cost=0 as an explicit free-card value, not a missing bubble
   (per B5-0334 confirmation + B5-0323 rule).

## Open questions (deferred to future tasks)

1. **Set 4/6/8 names**: unconfirmed. Second-source cross-check needed before
   trusting these names in any data field. Suggested source: Scyk site
   (https://www.skygem.net/b5.html) or per-expansion scan lists.
2. **SubType 20 ambiguity**: 118 SNRPG rows with SubType 20
   (ENHANCEMENT_*_CHARACTER | FLEET | LOCATION). Card text contains the
   attach-target answer but it's not a 1:1 code→enum mapping. Not relevant
   for cost-only backfill; relevant for a future subtype-restoration task.
3. **Race 8/9/10 (Drakh/Shadow/Vorlon)**: not in our Faction enum. A future
   model widening task (B5-0311 seam or independent) is needed before these
   rows can be fully addressed.
4. **ShowInFilter column**: always 0; dead metadata. Skip.
5. **B5-0355 text-authenticity gap**: bulk text backfill is unsafe until
   Adira/Du'Nar divergence is resolved. Cost-only remains the safe separable
   step.
