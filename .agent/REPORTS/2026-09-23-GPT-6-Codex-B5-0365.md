# B5-0365 — Contingency cards

## Implementation

Added `CardType.CONTINGENCY` and `ContingencyCard` with target type/race restrictions, trigger text, placed-under host link, face-down state, owner, and one-time reveal state. A host exposes only its contingency count so observers cannot inspect hidden card identities. The JSON loader hydrates typed contingency fields; no current card is typed `CONTINGENCY`, so the conformance suite uses a synthetic JSON fixture and the card pool was left unchanged.

The engine adds `PLAY_CONTINGENCY` and `REVEAL_CONTINGENCY`. Placement requires the card in hand, an available action, a playable faction, a valid target, and a host in the player's in-play zones. Race matching reads the host card subtype (such as `CHARACTER_NARN`) rather than its faction. Reveal is owner-gated and caller-driven: trigger detection is not available without contingency definitions. Revealed cards use the existing ID-keyed Event effect dispatcher, then detach and enter the owner's discard pile.

## Limits

The pool contains no contingency cards. The engine provides explicit placement and reveal actions, but cannot infer each card's printed trigger or special effect. Event parity means a revealed contingency can use a registered Event card ID; unregistered IDs follow the existing generic draw-one Event fallback. Existing host-removal flows do not yet sweep attached contingencies; the discard-if-host-leaves-play rule needs to be wired with host lifecycle/damage work.
