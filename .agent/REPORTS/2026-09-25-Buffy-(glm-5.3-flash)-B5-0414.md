# B5-0414 — UI audit of the post-B5-0310 controls (report-only)

Scope: `b5ccg/src/b5ccg/ui/` READ-ONLY under claim
`.agent/CLAIMS/B5-0414.json` (started 2026-09-25T04:52:00Z, clock-derived).
Zero code edits. JDK 1.8.0_292. Audited controls: Lead Fleet + Use Rotate
Effect (B5-0401), Attack + Heal + Repair (B5-0402), mercenary Bid (B5-0404),
Declare War (B5-0407) — for the B5-0328 defect class (stale selection
listeners, wrong-button enablement, selection/target staleness across
clearSelection, phase-gating holes). Line numbers refer to the current
working tree (MainWindow.java ~1560 lines).

## P0 — Heal / Repair / Lead Fleet / Attack are wired to the wrong selection
source; three of the four can never fire as gated

**MainWindow.java:792 + 1103 + GameBoardPanel.java (whole file).**
`selectedCard` is fed ONLY by the HandPanel selection listener
(`handPanel.setOnCardSelected`, line 792) over `human.getHand()`
(`handPanel.update(human.getHand(), ...)` line 1103). GameBoardPanel —
where Inner Circle, supporting characters, fleets, and locations RENDER —
has zero selection hooks (no ActionListener/MouseListener in the file;
grep-verified). Consequences, per control:

* **Heal (1207–1210):** requires the selected card to be in
  `human.getInnerCircle()` or `human.getSupportingRole()` — those characters
  live on the BOARD, not in hand, so `canHeal` can never be true for a real
  damaged character. Button is permanently dark in real play.
* **Repair (1212–1222):** requires `selCard instanceof FleetCard/LocationCard`
  with damage — again board-zone cards only. Permanently dark.
* **Lead Fleet (1336–1353):** `hasValidLeader` requires the selected card in
  IC/supporting — unreachable via a hand selection. Permanently dark.
* **Attack (1202–1206):** enablement is gated on `activeConflict` non-null,
  which B5-0409 (my report) proved never exists at human decision time
  either (synchronous resolution) — so Attack shares both defects.
* **Use Rotate Effect** is the ONLY new control whose selection source is
  reachable: `selectedAssistant` is set from the same hand selection, but a
  supporting assistant is ALSO not in hand — same defect. Its enablement
  (1369–1374) additionally requires `human.getAmbassador() != null`, which
  is true, but `selectedAssistant` can only be null. Permanently dark.

Net: **5 of the 6 new action controls are dead UI** — they render, they
gate correctly against the engine, but no user interaction can ever enable
them because the selection they read cannot contain an eligible card. The
B5-0401/0402 reports verified compile + headless gates only (their own
caveat: "manual click path is unexercised by headless suite" — this audit
is the missing manual-path verification, done statically).

**Smallest fix direction (NOT applied — report-only row):** give
GameBoardPanel the same `CardSelectedListener` callback HandPanel has
(mini-cards already know their card objects in drawZone), set
`selectedCard`/`selectedAssistant` from board clicks, and route through the
existing `updatePlayInitiateButtons()`/refresh cycle. No engine change.

## P1 — clearSelection does not reset the new selectors' selection state

**MainWindow.java:1523–1548.** `clearSelection()` resets selectedCard/
target/assistant/fleet and disables play/initiate/lead/rotate/attack/heal/
repair — good — but does NOT touch `warTargetSelector`,
`mercenaryBidAmountSelector`, or `contingencySelector` selections. These
are state-driven (re-gated every refresh), so the risk is limited to a
stale dropdown *value* shown to the user after a submit (cosmetic/
confusion class, B5-0310 P2). No illegal submit is reachable (every
listener re-gates through the engine rules). Severity LOW-MED.

## P2 — Heal enablement misses the rotated precondition (silent-refusal class)

**MainWindow.java:1207–1210 vs RulesEngine.canHealCharacter:23–34.**
Engine requires `!ch.isRotated()`; the UI `canHeal` omits that check. A
rotated-but-damaged IC character lights Heal, and the click is refused
silently inside the listener's rules gate (no log, no status update) —
exactly the B5-0310 "button lit but nothing happens" confusion class.
Moot until the P0 selection defect is fixed (the button cannot light at
all today), but must be included in any P0 fix. Severity MED (latent).

## P2 — Heal enablement misses the undamaged-IC aid path

`canHealCharacter` deliberately returns true for an undamaged, ready IC
character (rotate-as-aid, engine line 32–33), but `canHeal` requires
`ch.getDamageTokens() > 0` — the aid path can never be offered even after
P0 is fixed. Also latent. Severity MED (feature gap, not a rule break).

## P3 — Mercenary Bid reads offers.get(0) (single-mercenary assumption)

**MainWindow.java:546–557.** The bid listener and the offer label hardcode
the first offered mercenary (comment says "single-mercenary display
assumption"). With multiple offers a bid could target a card the user
never saw prioritized. The engine re-gates (canBidOnMercenary), so no
illegal action; and the pool carries zero mercenary cards (B5-0386), so
this is unreachable today. A selector mirroring the B5-0381 contingency
pattern is the fix shape. Severity LOW (data-pending).

## P3 — Attack auto-target picks the first VALID target, not the intended one

**MainWindow.java:474–486.** The Attack listener iterates participants and
committed cards and picks the first card passing `canAttackConflictParticipant`
— the user cannot choose among multiple opposing committed cards. With
B5-0346's per-participant board readout showing all committed cards, a
target selector (B5-0325 pattern) would match user expectation. Unreachable
today (P0: activeConflict never non-null at decision time). Severity LOW.

## Verified-sound controls (no B5-0328-class defects found)

* **Declare War (B5-0407):** selector repopulated + button re-gated every
  refresh (`updateDeclareWarButton` re-derives kind, actionTurn, and
  `canInitiateWarConflict` — MainWindow.java:1398–1425); listener re-gates
  identically at click. No staleness path found.
* **Reveal Contingency (B5-0381/0394):** positional index maps onto
  `getPlacedContingencies(human)` whose zone order is deterministic
  (GameState.java:140–146: IC → supporting → fleets → locations); refresh
  and click read the same list order; button gated on
  `hasUnrevealed && actionTurn`. Sound.
* **Support/Oppose (B5-0363):** enablement derives from
  `isWaitingForHumanConflictJoin()` + 4-arg legality each refresh; not part
  of the audited set but re-verified as the pattern the new controls should
  have followed.
* **clearSelection reachability:** every submit path that should clear
  selection does (lead-fleet, attack, heal, repair, bid listeners call
  clearSelection after submit); no stale-enablement path found beyond the
  P1 note.
