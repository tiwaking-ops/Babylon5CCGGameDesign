## Fixtures (three ledger copies, built from scratch)

| Fixture | Contents | Expected contract |
|---|---|---|

- `dup-census.ps1` exit: **1**
- stdout: `B5-0765 x2` (one line, non-empty)
- Verdict: **PASS** — exit 1 with non-empty census output naming the duplicated
  id. This pins the **duplicate detection** contract: the census can FAIL.

### FIXTURE B — clean single id

- `dup-census.ps1` exit: **0**
- stdout: empty
- Verdict: **PASS** — exit 0 with empty stdout. This pins the **clean ledger**
  contract: the census exits 0 and emits nothing on a clean ledger.

### FIXTURE C — dup id inside a QUEUE note line only

- `dup-census.ps1` exit: **0**
- stdout: empty
- Verdict: **PASS** — exit 0 with empty stdout even though the string
  "B5-0765" appears inside a QUEUE narrative line. This pins the **lead-pipe
  anchor** contract: the regex anchored on `^\|+\s*(B5-\d{4}[a-z]?)\s*\|`
  does NOT match an id mention inside a prose/QUEUE line, so the census does
  not false-positive on narrative text. The duplicated id is correctly ignored
  when it is NOT on a task row.

- `dup-census.ps1` exit: **0**
- stdout: empty
- Verdict: **PASS** — the actual `.agent/TASK_LEDGER.md` is clean.

## Reusable lesson

A duplicate-ID census contract is pinned by THREE independent fixtures, not
one: a dup-positive ledger (exit 1 + names the dup), a clean ledger (exit 0 +
empty), and a prose-only id mention (exit 0 + empty, proving the lead-pipe
anchor does not false-positive on narrative text) — because a single
clean-ledger fixture cannot tell "census always silent" from "census silent
on clean"; the dup MUST be able to fail for the contract to mean anything.
