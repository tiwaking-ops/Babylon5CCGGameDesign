# B5-0613 — run-queue.ps1 Get-LedgerRows fix (item 1 of 5 in row scope)

## What was done

Get-LedgerRows in `.agent/run-queue.ps1` filtered rows with the single-leading-pipe regex
`^\|\s*(B5-\d+)\s*\|`. That anchor requires exactly one leading pipe before the ID, so any
double-pipe row (the defect class produced by prior close-outs) was invisible to the runner.

Changed the regex to `^\|+(?:\s*(B5-\d+)\s*\|)` (one or more leading pipes) and changed the
ID-cell extraction from `$parts[1].Trim()` to "first split cell matching `^B5-\d+$`" so
double-pipe rows resolve their ID from cell 2, not cell 1.

Added a self-check: the function now asserts that the number of rows it returned equals the
number of ledger lines matching the tolerant pattern. If the two differ, it writes a warning
that a row filter is silently hiding rows. This makes the defect class self-reporting going
forward.

## Verification

- Old single-pipe regex matched 301 of 312 ledger lines (11 double-pipe rows missed).
- New tolerant regex matches 312 of 312.
- Self-check passes: rows collected (312) == tolerant-pattern matches (312).
- Dry-run (`-DryRun -MaxIterations 1`) now sees all rows; queue correctly reports drained
  only after B5-0613 itself is claimed (the only remaining OPEN without a live claim).

## Reusable lesson

A ledger-query tool that anchors on a single leading pipe will silently miss every
double-pipe row, and the missed rows include OPEN tasks — so the tool's own "queue drained"
stop condition can fire while claimable work sits invisible; the fix is a tolerant leading-pipe
regex plus a self-check asserting returned-row count equals pattern-match count, so the class
reports itself rather than hiding.
