# B5-1462 — Tool-stamp claim creation times

## Finding that shaped the design

The task asked to "extend the claim-creation path". Measured: **there was
none**. No tool in `.agent/` writes claim files — `run-queue.ps1` only reads
claims for offer/liveness/refusal, and every claim file on disk was hand-
authored agent prose. That is precisely the weakness the clock-integrity
report names ("never let an agent author a timestamp a decision depends on"),
and B5-1047's future-dated claim is the standing live example. So the creation
half was added as a new tool.

## Change

New `.agent/tools/new-claim.ps1`:

* **Create mode** stamps `started_utc` from `[DateTimeOffset]::UtcNow` at the
  moment of writing — the tool authors the timestamp, never the agent —
  refuses an existing claim file (atomic-create per `.agent/CLAIMS/README.md`),
  writes UTF-8 strict JSON, then runs the **acceptance check**: the payload's
  `started_utc` vs the new file's `LastWriteTimeUtc` within 60-minute
  tolerance, so a tool-stamped liveness signal survives bulk-mtime events
  (clock-report rule §6.3).
* **`-VerifyOnly`** runs the same probe read-only against any claim, with a
  distinct 0/1/2 exit contract: 0 AGREE, 1 DISAGREE/unparseable/refused,
  2 MISSING — absence deliberately distinct, per the B5-0597 absent-signal
  rule (UNKNOWN is never folded into another verdict).
* Reap semantics untouched; the tool never deletes and never edits the ledger.

## Verification

* Scratch fixture (git-ignored `b5ccg/out/scratch-b51469/`): **7/7 PASS** —
  create-stamps-and-accepts; near-zero payload-vs-mtime delta; refuse-existing
  leaves the file byte-untouched; invalid id refused; verify AGREE; forged-
  future payload DISAGREE; MISSING exit 2.
* Live store: `-VerifyOnly` on the B5-1462 claim itself → AGREE
  (delta −0.175 min).
* AST tokenize 0 parse errors; `sh compile.sh` exit 0 (JDK 8, -source 6);
  post-write gates: run-dup-census exit 0; row reads 7 pipes / doubleLead no.

## Self-caught defects during the fixture loop

Two PowerShell 5.1 traps, both fixed and recorded in the tool header:

1. `[DateTime]::TryParse(s, [ref]$parsed)` fails overload resolution when
   `$parsed` is null-typed — must init to `[DateTime]::MinValue`.
2. **`exit (fn)` captures the function's `Write-Output` strings**, folding the
   int verdict into an Object[] whose first element coerces to 0 — the forged-
   payload refusal path reported success. Diagnostics moved to `Write-Host`;
   the verdict travels alone.

## Reusable lesson

An `exit (fn)` wrapper silently discards the function's integer verdict when
the function also emits strings — PowerShell folds both into an Object[] and
coerces the first string, so the refusal path reported success. A check that
can fail must carry its verdict in a dedicated channel, never mixed into prose.
