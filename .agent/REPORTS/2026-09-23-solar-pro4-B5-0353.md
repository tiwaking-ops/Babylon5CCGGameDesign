# B5-0353 — Fleet-class vocabulary research

## Task
Derive the closed fleet-class set from printed card texts for the Limited Strike `fleetSubtypes` filter. Mapping table only; **no JSON edits**.

## Methodology
1. Enumerated all 80 FLEET cards across `premiere.json` + `deluxe.json` (446 total cards).
2. Read each card's `text` field for class-descriptive terms.
3. Cross-referenced card ID naming patterns (`fleet_<class>_<faction>`) against printed texts.
4. Checked the Limited Strike card (`conf_limited_strike`) printed text as ground truth.
5. Checked the B5-0336/B5-0352 participation data and the D6/D9 proposals for the intended vocabulary.

## Key distinction: `subtype` vs `fleetClass`

The JSON `subtype` field on FLEET cards is **faction-based** (`FLEET_HUMAN`, `FLEET_MINBARI`, `FLEET_CENTAURI`, `FLEET_NARN`, `FLEET_NON_ALIGNED`). This is already populated for all 80 fleet cards and is **not** what the `fleetSubtypes` filter consumes.

The `fleetClass` field (added by B5-0336 on `FleetCard.java`) is **class-based** and is the field that `Participation.fleetSubtypes` checks. It is **currently null on every fleet card** — population is the separate data task (post-B5-0353). B5-0353's job is to define what values that field should accept.

## Ground truth: Limited Strike printed text

> "Military conflict. Winner gains 1 Influence. **Only Picket, Colonial, and Utility fleets may participate.**"

Card `conf_limited_strike` (PREMIERE), `participation` = `{"cardTypes":["FLEET"], "fleetSubtypes":["PICKET","COLONIAL","UTILITY"]}`.

This is the authoritative declaration of three fleet classes: **PICKET**, **COLONIAL**, **UTILITY**.

## What this means for Limited Strike

Limited Strike's `fleetSubtypes: ["PICKET","COLONIAL","UTILITY"]` covers **3 of 20 classes** (15% of the vocabulary). Those 3 classes cover **11 of 80 fleet cards** (PICKET×4 + COLONIAL×4 + UTILITY×3 = 11). The remaining 69 fleet cards would be excluded from a Limited Strike conflict by this filter.

## Open questions (for the data task, not this report)

1. **Battle class granularity.** Should FIRST_BATTLE / SECOND_BATTLE / THIRD_BATTLE be three separate classes, or should they collapse to a single BATTLE class with a "tier" sub-distinction? The card texts treat them as distinct ("primary" vs "reserve" vs "veteran/elite"), and the card IDs use separate prefixes. Recommendation: keep as three separate classes until a proposal argues for collapse.

2. **Non-Aligned fleet classes.** Groups C and D are race-specific, not faction-cycle classes. Should DRAZI/IPSHA/MARKAB/VREE be valid `fleetClass` values, or should Non-Aligned fleets use a different mechanism (e.g., null fleetClass + separate Non-Aligned participation rule)? The B5-0336 proposal §3.6 doesn't address Non-Aligned explicitly. The current engine code (`Participation.canCommit`) would accept any `fleetClass` string that matches a `fleetSubtypes` entry, so DRAZI/etc. would work mechanically if a future conflict card listed them.

3. **FLEET_OF_THE_LINE and WARLEADERS.** These are unique single cards with no faction cycle. Their class values are ad-hoc. If a future conflict card wanted to restrict to "fleet_of_the_line" class, it would only affect 1 card per deck. This is degenerate but not incorrect.

4. **Deluxe-only fleet cards.** The deluxe set has the same fleet class distribution as premiere (same 20 classes, same card counts per class, except deluxe has no additional classes). No new vocabulary emerges from deluxe.

5. **UTILITY count discrepancy.** UTILITY has 3 cards per set (Human, Centauri, Narn) — Minbari has no utility fleet. This is a card-design fact, not a vocabulary issue. The closed set still includes UTILITY as a valid class; Minbari simply has no card of that class.
