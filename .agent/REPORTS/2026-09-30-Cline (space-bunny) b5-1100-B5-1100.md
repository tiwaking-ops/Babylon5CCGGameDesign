## The exact predicate that excludes it

`b5ccg/src/b5ccg/engine/StarterDeckBuilder.java:154`

```java
if (r != Rarity.UNCOMMON && r != Rarity.RARE) continue;
```

Evaluated for the withdrawn record: `rarity != UNCOMMON` is `true` and
`rarity != RARE` is `true`, so the guard is `true` and `continue` fires at
line 154. **Line 155 is never reached.**

This is the load-bearing detail. Had the record's rarity been `UNCOMMON` or
`RARE`, line 155 would have been evaluated — and it would have **admitted** it:

```
had it passed, isPlayableBy(HUMAN)=true
had it passed, isPlayableBy(MINBARI)=true
had it passed, isPlayableBy(CENTAURI)=true
had it passed, isPlayableBy(NARN)=true
```

`faction=ANY` and `Faction.isPlayableBy` returns `true` for `ANY` against any
player faction. The card is therefore exactly **one predicate** away from every
random slot of every starter deck. Nothing in lines 152-156 mentions withdrawal;
the safety is a property of the enum enumeration omitting `RARE_WITHDRAWN`, not
of a rule. That is a materially different statement from "withdrawn cards are
excluded", and it is the finding worth carrying forward.

## Latent finding — NOT fixed (execution-only scope)

The **fixed** path, `StarterDeckBuilder.java:114-127`, applies **no rarity
guard**. It resolves `byId`, else falls through to `findFixedByTitle`, and adds
whatever card it lands on.

Compounding it: `DeckLoader.loadBothSets` keeps a Deluxe record in preference to
a Premiere record of the same title, so the Premiere `RARE` twin
`agenda_as_it_was_meant_to_be` is **absent from the pool** (probe: `other pool
record same title = -`). The `RARE_WITHDRAWN` Deluxe record is the sole
representative of that title in the pool.

Counterfactual, measured in-probe without editing the resource:

```
premiere id agenda_as_it_was_meant_to_be title=As It Was Meant To Be
byId.get(premId) in pool = null -> falls through to title match
byTitle.get(premId's title) = de_agenda_as_it_was_meant_to_be rarity=RARE_WITHDRAWN
VERDICT: a fixed list naming agenda_as_it_was_meant_to_be would place
rarity=RARE_WITHDRAWN into a FIXED slot, because the fixed path (lines 114-127)
applies no rarity guard at all.
```

So a withdrawn card could reach a starter deck's fixed 50 today, and the only
thing preventing it is that no fixed list happens to name that id. That is safe
by **data accident**, not by code. No fixed list does name it — 187 entries
scanned, 0 hits — so this is a latent exposure, not a live defect.

**Left for B5-1097** (OPEN, owns the pool-assembly `RARE_WITHDRAWN` exclusion).
An exclusion at pool assembly would close both routes at once, including this
one, which is why it is the right home for the fix. This row changed no file.
