## Three directions sized

1. **Backup rotation** — ruled out as not implementable without tool support: requires a write wrapper around every ledger write or participation by the truncating writer, which is unidentified (no tool, script, or report in the repo writes a .bak). Not addressable against an unknown actor.
2. **Append-only discipline** — ruled out as not implementable without tool support + fleet process change: requires all current ledger writers to switch to a delta-and-merge protocol simultaneously, plus a merge tool. Not implementable without a fleet-wide coordination change.
3. **Backup-pointer convention** — the only direction adoptable today with no tool change. A `.agent/TASK_LEDGER.md.backup-pointer` file holds one line `<sha256> <UTC>` of the last known-good ledger. Any agent that writes the ledger writes the pointer before opening the ledger for write and updates it after a successful close-out write. Boot-time readers fall back to the .bak on mismatch and emit a loud warning rather than silently operating on a truncated file. The one small tool addition that makes this rote (a hash-check patch in `run-queue.ps1`) is gated behind human approval and is explicitly NOT written by this task.

## Proposed slice

Backup-pointer convention only. Backup rotation and append-only discipline are left out of this proposal entirely.

## No tool / ledger / .bak changes

This task touched no tool, no script, no ledger row (beyond its own close-out), and no .bak file. The proposal is a documentation artifact only.

## Open questions (recorded, not answered)

1. **Who truncates the ledger?** Neither incident has identified the actor. This proposal is defense-in-depth — it reduces the cost of the next incident regardless of cause — not a fix for the root cause.
2. **Pointer authority under multi-agent writes.** The pointer certifies the hash of the file as written, not correctness. A defective file with a matching pointer is still defective; the post-write duplicate-ID census and the ledger-query pipe check are the correctness signals, independent of the pointer.
3. **Pointer file lifecycle.** Git-ignored (coordination state, like claims/heartbeats) vs tracked (survives a working-tree wipe) — left undecided; honor-system adoption by individual agents does not require a decision.

## Reusable lesson

A live-file-plus-stale-backup pair with identical timestamps is the signature of a truncation event, not a slow drift; a backup-pointer file (hash of last known-good state) converts the detection of that event from an agent noticing an implausible census count to an automatic boot-time check — and it is the only one of three hardening directions that an agent can begin honoring today without a tool change or a fleet decision.
