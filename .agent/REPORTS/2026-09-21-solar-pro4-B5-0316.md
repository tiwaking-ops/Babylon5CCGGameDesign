# B5-0316 — conflict participation visualization (F7), implementation report

Agent: `solar-pro4` (solar-pro4:free). Task: B5-0316 (OPEN → DONE). Scope:
`b5ccg/src/b5ccg/ui/` (GameBoardPanel.java only — reads model, does not modify it).

## What changed

**One file:** `b5ccg/src/b5ccg/ui/GameBoardPanel.java`, inside the existing active-conflict
banner block (`paintComponent`, the `if (state.getActiveConflict() != null)` region).

Added a centered sides readout directly beneath the existing "CONFLICT: <title> [<type>]"
banner (2 lines of separation, same centering math as the banner itself):

    sides committed (B5-0309):
    <supporters.size()> support (<supportTotal()>)   |   <opposers.size()> oppose (<oppositionTotal()>)

Example on a live 4-player conflict where the initiator has one supporter and two opponents
with committed cards: `1 support (18)   |   2 oppose (22)`.

The readout uses `Conflict`'s D14 sides API exactly as the task spec requires:
`getSupporters()`, `getOpposers()`, `supportTotal()`, `oppositionTotal()`. No new model
accessors, no new model state, no engine touching — purely a `GameBoardPanel` rendering
addition.

## What it shows (and what it does not)

**Shows:**
- Number of committed players on each side (`supporters.size()` / `opposers.size()`).
- Total stat value committed on each side (`supportTotal()` / `oppositionTotal()`), i.e. the
  summed `getPrimaryStatValue(conflictType)` of every committed card on that side.

**Does not show (by design, recorded as future work, not scope):**
- Per-participant card breakdown (which player committed which card, and at what value). Per
  D14 decision (2) in `docs/DECISIONS.md`, per-participant visibility is future work "when
  JOIN actions become player-visible." The readout deliberately stays at the side-total level.
- A separate visual for the initiator vs joiners (the API already distinguishes the initiator
  via `getInitiator()`; the banner line could be extended later but that is not part of B5-0316).
- Anything when no conflict is active: the whole block is inside the `if (state.getActiveConflict() !=
  null)` guard, so it is invisible during non-conflict phases. This is correct — there is nothing
  to show.
