## What the merge changed

The merge is not a concatenation. Merging forced the four censuses onto one ordering,
and two things surfaced that none of them could see alone.

**The trigger exposure was wrong in the row text and in the report it names.**
B5-1153's "12 values covering 103 records undispatched" is superseded by my B5-1347
measurement of **113 records over 14 values**. The cause is `WON_DIPLOMACY`: half its
records (`aftermath_united_front`, `de_am_united_front`) are in neither dispatch set,
so the value is not fully covered and the count of values needing work is 14, not 12.
Any ranking that consumed 103/12 — including this row's own task text — was ranking
against a number that was never the undispatched total.

**Three of the four censuses measure different axes, and one of them is not a
coverage gap at all.** B5-1127 already warned that AFTERMATH's "0 registered" is
*correct* because the 117 records key on `triggerCondition`, and that calling them
"uncovered" would be wrong in any count. Writing the backlog forced a fourth axis
into the open alongside registration, trigger eligibility and cost composition:
**type routing**, from B5-1341. Of the four, only registration and type routing are
coverage gaps. Trigger eligibility is a feature question; cost composition is a
correct-code-over-empty-set question. The proposal says so explicitly in a section
titled "Read this before claiming anything", because the failure mode for a merged
backlog is precisely a reader treating four axes as one queue.

**Two entries carry receipts that change what a naive implementation would do.** The
B5-1173 premiere-id trap (`conf_non_aligned_support` is absent from the deduped pool,
so a premiere-id `FREE_SPONSOR` entry wires a dead key), and B5-1173's rulebook gap
(`sponsorWaiver` expresses only the cost half of §Free, so a `FREE_SPONSOR` entry
would silently under-implement immediacy and no-rotate). And B5-1125's CONFLICT slice
has the same shape: the `influenceReward` clause already lands generically, so
re-adding it would be 13 rows of noise.

## Reusable lesson

When merging several censuses into one queue, the merge's first job is to write down
what each census *measures*, because the axes read alike and rank alike until you
put them side by side — one of them turned out not to be a gap at all. The second job
is to re-derive any figure that arrived via a chain of reports rather than from
source; the exposure number in this row's own task text was wrong, and it was wrong
in a direction that would have silently deprioritised a half-covered value.
