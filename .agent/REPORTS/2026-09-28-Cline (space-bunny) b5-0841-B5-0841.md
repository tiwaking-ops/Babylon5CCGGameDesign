four rows it names, no execution, no file edits to the script, no commit. The

## 4. The re-run hazard, demonstrated without running the script

The row's second finding is that re-running would append stale rows and create
real duplicate IDs. I proved it **on a temp copy**, never on the live ledger:

* copied `.agent/TASK_LEDGER.md` to `%TEMP%\b5-0841\TASK_LEDGER.md`;
* extracted the four row bodies from `seed_tasks.sh` **as text** with a regex
  (the file was read, not executed) and appended them to the copy;
* ran the shipped census against the copy:
  `run-dup-census.ps1 -LedgerPath %TEMP%\b5-0841\TASK_LEDGER.md`
  → `B5-0511 x2`, `B5-0512 x2`, `B5-0513 x2`, `B5-0514 x2`,
  `duplicate-ID census: FAIL`, **exit 1**;
* the live ledger's byte length was measured before and after the exercise and is
  unchanged at **959171**, and the live census still reads
  `PASS (0 duplicate task IDs)` exit 0.

So the hazard is not hypothetical: the tool that exists to police duplicate IDs
would correctly fail the repository the moment anyone re-ran this file, and
because the queue keys status by ID, the second copy of each row silently wins.
The append order in the file is 0511, 0513, 0512, 0514, and the ledger's own
order is 0511, 0513, 0512, 0514, so the **appended** row is last in both, meaning
the stale `OPEN` copy would be the one the queue reads. That is the worst
direction: four finished tasks would read as available work.

## 5. The hardcoded path — the B5-0306 bug class, confirmed

Line 1 is `cd /c/temp/projects/Babylon5CCGGameDesign`, an **MSYS** absolute path.
Measured on this machine, which is the machine that wrote it:

* `Test-Path /c/temp/projects/Babylon5CCGGameDesign` → **False** under
  PowerShell, which resolves it as `C:\c\temp\...`;
* run under PowerShell, `cd /c/temp/...` fails with
  `Cannot find path 'C:\c\temp\projects\Babylon5CCGGameDesign'`;
* the only `bash` on PATH is `C:\Windows\System32\bash.exe`, which is the **WSL
  relay**, and it fails: `WSL (9 - Relay) ERROR: CreateProcessCommon:818:
  execvpe(/bin/bash) failed: No such file or directory` — there is no usable
  MSYS shell on this box to interpret the path at all;
* `python3` resolves first to
  `C:\Users\Tiwa Pene\AppData\Local\Microsoft\WindowsApps\python3.exe`, which is
  the **0-byte Microsoft Store alias stub**, not an interpreter. The real one is
  at `...\AppData\Local\Python\bin\python3.exe` (591360 bytes).

Conclusion on validity: the hardcoded path is valid on **no currently reachable
shell on this machine**, and on any other machine only if the repo happens to sit
at the same absolute path. The script is not merely non-portable, it is
**currently unrunnable**, which removes "someone might still use it" as a defence
of keeping it. This is exactly the B5-0306 class (absolute POSIX path handed to
native Windows tooling) and the heredoc-plus-Store-alias combination adds a
second failure the earlier row did not name.

## 6. Recommendation

**Tracked removal (`git rm seed_tasks.sh`), with the two facts recorded in
DECISIONS so the reasoning is not lost.** Reasons, in priority order:

1. **It is a live corruption vector.** One command from the repo root appends
   four stale `OPEN` rows to the shared governance ledger, and the shipped
   duplicate-ID census proves it fails the repo. Keeping an executable
   ledger-appender at the root is the failure B5-0618 exists to prevent.
2. **It is residue with no remaining consumer.** All four rows are `DONE`, and
   nothing in the tree invokes it.
3. **It is unrunnable as written**, so no workflow is broken by removing it.
4. **Its tracked status is an accident**, contradicted by eight same-day reports
   that classified it as scratch and by two checkpoint commits that deliberately
   excluded it.

Relocation into an archive is the **weaker** option and is not recommended: an
archived copy of a working appender is still a working appender to anyone who
finds it, and the repo already has `docs/archive/` plus the committed `418664de`
blob as the durable record. Git history *is* the archive for a 21-line file.

If a human prefers to preserve the file rather than delete it, the minimum safe
change is relocation to `docs/archive/` **and** replacing line 1 with a
repo-relative `cd "$(dirname "$0")/.."` — but note this row is report-only, so
neither change was made. The `download_cli.ps1` sibling committed in the same
sweep has the same "root dropping" character and is **not** in this row's scope;
flagged, not assessed.
