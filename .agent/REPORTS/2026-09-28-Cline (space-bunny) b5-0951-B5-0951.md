## The branch taken, and why

B5-0951 asked which of two branches to take, and required the answer to be stated with
its reason. **I took branch 2: the file is non-conforming, the schema is complete, and
the remedy belongs to the file's owner or a human.** Full reasoning in
`docs/proposals/heartbeat-released-state-ruling-proposal.md`. Three measured reasons:

1. **`state` has no behavioural consumer.** `.agent/` holds 15 scripts; the only readers
   of a heartbeat payload's `state` are `validate-heartbeats.ps1` (enum check l.145, plus
   a display column l.201) and `migrate-heartbeats.ps1` (coercion input l.199).
   `run-queue.ps1` never reads it — liveness comes from the three-signal rule and
   `live_claims`. So widening the enum to admit `released` would change **no verdict any
   tool in this repo produces**; it would only change the validator's exit code.
2. **The meaning is already carried, in the right field.** The offending file has
   `live_claims: []` and `current_task: null`. "Claim released, holds nothing" is stated
   twice already, machine-readably, in enum-free fields. `released` is **redundant**, so
   the premise of the widen branch — a real state the schema cannot express — is absent.
3. **The `busy` precedent does not transfer.** `busy` was added by human approval
   (A1.2, B5-0623) because a *live working* agent could not satisfy the schema. This
   file's payload is fully schema-satisfying; the one bad token sits where the payload
   already said the same thing correctly.

Because branch 2 forbids editing the foreign file, and because the row separately forbids
widening the enum "merely to make the validator green", **neither remedy was available to
me and I took neither.**

## The residual red is correct, and I am reporting it as red

`validate-heartbeats.ps1` **still exits 1**, unchanged from boot. This is the honest
outcome, not an unfinished task: the only two actions that could turn it green are the two
the row forbids (edit the foreign file; widen the enum without recorded meaning). A green
validator here could only have been bought by breaking a rule. I would rather hand the
next agent a red validator with a documented reason than a green one obtained illegitimately.

Concretely, the one-line fix available **to the owner** or a human is
`state: "released"` → `state: "idle"` in
`.agent/HEARTBEATS/Cline (space-bunny) b5-0941.json`. That loses no information, because
the claim-release fact lives in `live_claims: []` and `current_task: null`. I did not
apply it: the file is foreign, untracked in git, and the binding README says never edit
another agent's file.

## New finding, out of scope, reported not fixed: `migrate-heartbeats.ps1` has drifted

`.agent/tools/migrate-heartbeats.ps1:55` carries `$ValidState = @('active','idle')` — its
own copy of the enum, **missing `busy`**, which the human-approved A1.2 amendment added to
the validator's copy. Its l.199 coerces anything outside its list, defaulting to `idle`
(l.201). Consequence: **running that tool for real would silently rewrite every `busy`
heartbeat in the store to `idle`** (2 files today) and would silently normalise this
`released` file too — performing, as a side effect, the very edit no agent is permitted
to make by hand. It is the B5-0623 lesson recurring one directory over: *two copies of a
list is one copy too many.*

This file is not in my claimed scope, so I left it byte-identical. It warrants its own
row: delete the second copy and read the canonical enum, or make the tool refuse to run
when the two disagree.
