## Method

lines 23–1313), then each classified on the row's three axes by greps run this
pass: production reachability (consulted by `GameController` — the real
GameAction path — or delegating through another consulted gate), and suite
assertion coverage (`rules.<gate>(...)` occurrences in
`HeadlessConformanceTest.java`). Model-side: `Conflict.canCommitCard` /
`canAddParticipant` / `canJoinConflict` reached via `GameController`'s commit
path and asserted in the PAR section; `ContingencyCard.canTarget(host)` +
`controlsInPlay` reached via PLAY_CONTINGENCY. The row's B5-0609-class
prohibition was honoured: no coverage inferred from ledger prose or suite
comments — every coverage number is a grep count of real `rules.<gate>(` call
sites.

## Findings, ranked

1. **DEAD GATE — `canPlayCard` (:901), P1/HIGH.** Zero production callers: the
   controller's `case PLAY_CARD` delegates straight to `applyGenericCardPlay`,
   which consults only `canSponsorAgenda` (agendas) and removes the card from
   hand. In-hand and faction-playability are enforced only indirectly — by
   whoever built the action (UI, AI) — so the *engine* would accept a
   PLAY_CARD GameAction for a card not in hand or not playable by faction if
   any future caller constructed one. This is the exact defect class B5-0302
   fixed for INITIATE_CONFLICT ("was dead code — zero callers"), now on the
   PLAY_CARD path. Reachability and correctness are different defects; this
   one is "correct but unreachable".
2. **INDIRECT-ONLY GATES (P2/MEDIUM, 5 gates).** `canHealCharacter`,
   `canRepairCard`, `canPromote`, `canDeclareWarConflict`,
   `canInitiateWarConflict` are enforced on the AI-offer path (and ui/probes)
   but the controller trusts the action without consulting the gate when a
   human submits the same action. The AI path's legality guarantees (B5-0202c
   line: 4/4 legal every smoke run) do not extend to the human path. Smallest
   fix if ever approved: GC pre-validate with the same `rules.can*` the AI
   uses — one line per case, no behaviour change for legal play.
3. **`canUseAssistant` — NOT dead, reclassified after verification.** Zero
   direct production callers, but `canUseRotateEffect` (GC-consulted)
   delegates to it (:1214) and two execute paths guard through it
   (:1161/:1180). Listed because a naive "zero callers" sweep would have
   misfiled it as dead — the same false-negative class the B5-0618 wave
   recorded for suite coverage.
4. **Unasserted-but-reachable (P3/LOW).** `canInitiateWarConflict` has zero
   HeadlessConformanceTest assertion sites (its checks live in
   HeadlessWarConflictProbe + HeadlessHumanSeatProbe, which RUN_TESTS does not
   run). `canJoinConflict` has 1 direct site (its behaviour is largely
   asserted through the conflict sections). `canPlayContingency` 1 site.

## The two rulebook worked examples (:826–:829) against the card pool

Both named cards **exist** in premiere.json (title-deduped deluxe copies) —
and neither implements its rulebook target rule:

- **"Rivalry"** — pool record: AFTERMATH_DIPLOMACY_PARTICIPANT, text "Play
  after participating in a Diplomacy conflict. Gain 1 Influence if you were
  the initiator or if you supported the winner." **No target requirement
  exists.** The rulebook :826 example (target two Inner Circle characters
  other than the ambassador, same controller) describes a *different card
  design* than the pool's authored design. Data-gate finding, not an engine
  gap: implementing the :826 requirement against this pool would override the
  authored design layer (B5-0388 ruling).
- **"Test Their Mettle"** — pool record: a plain CONFLICT_DIPLOMACY ("Winner
  gains 2 Influence. Loser's ambassador is face-down until healed."). **No
  race-target restriction exists.** The :828 rule (refuse an unplayed race as
  target) is unimplementable against a card that takes no race target at all.

Zero engine references to either card by id or title (grep). Conclusion: the
:823 *principle* is partially embedded (requiresTarget :897, canJoinConflict,
canPlayContingency host checks, war-target in-play checks), but **both worked
examples are data-gated, not engine-implementable** — there is no card in the
pool whose text exercises them.

## Proposed slice (at most one, per the row)

**P1 slice: wire `canPlayCard` into the PLAY_CARD case** (one guard line in
`GameController`, engine scope only, mirroring B5-0302's fix class) + one
suite section asserting the gate refuses a not-in-hand card and a
faction-unplayable card through the real action path. This is the only
finding that is an engine defect today rather than a design/data question.
