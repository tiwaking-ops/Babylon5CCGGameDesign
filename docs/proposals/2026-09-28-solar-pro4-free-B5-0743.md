# Backup-pointer convention for TASK_LEDGER.md

## Context

Two full-truncation incidents have now destroyed `.agent/TASK_LEDGER.md` and been
recovered from the adjacent `.agent/TASK_LEDGER.md.bak`:

| Incident | When | Live file state found | Backup state | Recovery |
|---|---|---|---|---|
| B5-0733 (first) | 2026-09-27 ~10:32Z | 2 lines, 1 row (B5-0695 BLOCKED) | 890 lines, 380 rows, strict superset of HEAD | Restored .bak verbatim, re-applied B5-0695 BLOCKED close-out |
| QUEUE 0735..0747 (second) | 2026-09-27 ~10:32Z (same instant per LastWriteTimeUtc) | 2 lines, 1 row | 380 rows, zero duplicate IDs, already contained B5-0733 DONE row | Restored .bak verbatim, re-applied me-so-poor B5-0695 BLOCKED |

Forensics for both incidents (recorded in B5-0733 and QUEUE 0735..0747 before any
write): the live file and the .bak carry **identical `LastWriteTimeUtc` and
`CreationTimeUtc`**, so the .bak was created in the same instant the live file
shrank — a single write event, not slow drift. The truncating writer is **not
identified** in either case: no tool, script, or report in the repository writes a
.bak, so the .bak is attributed to an unrecorded actor and the destructive-write
path remains unidentified (B5-0733 explicitly records this as the open half of that
task).

The consequence of both incidents: 14–15 OPEN rows became invisible to every agent,
the queue reported a false all-clear, and recovery depended on the .bak being present
and correct at the moment an agent booted and noticed the mismatch. That is a
fragile guarantee — if the .bak is absent, wrong, or itself truncated, there is no
in-repo recovery path.

## Three hardening directions

### 1. Backup rotation (needs tool support)

A rotation convention would maintain a small ring of .bak files (e.g.
`.bak.0` = most recent, `.bak.1` = previous) with an atomic swap on each write so a
truncation that destroys the live file cannot also destroy the only backup. This
requires either the truncating writer to participate (unknown actor — not addressable)
or a wrapper around every ledger write that creates the rotation. Neither exists today.
**Not implementable without a tool change and identification of the write path.**

### 2. Append-only discipline (needs tool support + process)

An append-only discipline would write new ledger rows to a separate delta file and
merge them into the canonical ledger only at close-out, so the canonical file is
opened for write rarely and briefly. This bounds the window of exposure but does not
eliminate it — a truncation that fires during the merge window still destroys the
canonical file, and the delta file is a second point of failure. It also requires all
current ledger writers (many agents, many sessions) to switch to the delta-and-merge
protocol simultaneously, which is a fleet-wide coordination change. **Not implementable
without a tool change and a fleet protocol change.**

### 3. Backup-pointer convention (no tool change to adopt; one small tool addition to
make rote)

A **backup-pointer file** — `.agent/TASK_LEDGER.md.backup-pointer` — is a small plain
text file that holds one line: the SHA-256 (or SHA-1) hash of the last known-good
`.agent/TASK_LEDGER.md`, optionally with a UTC timestamp. Agents adopting the
convention write the pointer **before** opening the ledger for any write, and update
it **after** a successful close-out write. Boot-time readers (specifically
`run-queue.ps1` and the manual census fallback) check the pointer at the start of
their ledger read: if the live file's current hash does not match the pointer, the
reader treats the live file as suspect and falls back to the .bak (which it hashes
and compares to the pointer too), emitting a loud warning rather than silently
operating on a truncated file.

This convention is **adoptable today with no tool change** — any agent that writes the
ledger can write the pointer as part of its existing read-modify-write, and the
byte-format is stable enough that a future tool addition can consume it without
re-parsing the ledger. The one small tool addition that makes it rote rather than
honor-system is a single hash-comparison check in `run-queue.ps1` at the point where
it first reads the ledger; that addition is a patch to one file, not a rewrite, and is
blocked until a human approves the tool edit (this repo's external-tool gate).

## Sizing

| Direction | Implementable with no tool change | Needs tool support | Needs process/fleet change |
|---|---|---|---|
| Backup rotation | No — requires a write wrapper or writer participation | Yes — rotation wrapper or writer modification | No |
| Append-only discipline | No — requires all writers to adopt delta protocol | Yes — merge tool or writer modification | Yes — fleet-wide protocol switch |
| Backup-pointer convention | **Yes — the pointer write is a line any agent adds to its existing ledger write; the .bak is already the fallback storage** | Yes — one hash-check patch in `run-queue.ps1` to make it rote (optional; honor-system works) | No — individual agents can adopt independently |

The backup-pointer convention is the only direction that an agent can begin honoring
today without waiting for a tool change or a fleet decision. It does not prevent the
truncation — nothing short of identifying and stopping the truncating writer does that
— but it makes the **detection** of a truncation automatic at boot rather than
contingent on an agent noticing that the census returned an implausibly small row
count and manually comparing file sizes.

## Proposed slice (at most one)

**Adopt the backup-pointer convention. Do not touch backup rotation or append-only
discipline in this proposal.**

Concretely:

1. **Convention text** (this proposal, once merged): any agent that writes
   `.agent/TASK_LEDGER.md` writes `.agent/TASK_LEDGER.md.backup-pointer` containing
   one line `<sha256> <UTC>` of the pre-write live file before opening the ledger for
   write, and updates the pointer after a successful write. The .bak is the recovery
   storage; the pointer is the detection signal.

2. **Boot-time check** (future tool patch, gated behind human approval): `run-queue.ps1`
   hashes `.agent/TASK_LEDGER.md` at the start of its ledger read and compares to the
   pointer; on mismatch it hashes `.agent/TASK_LEDGER.md.bak` and, if that matches,
   uses the .bak and emits a warning, otherwise it emits a loud failure and exits
   non-zero rather than operating on a truncated file. This is a patch to one file,
   not a rewrite; it is **not** part of this proposal's deliverable and is not written
   by this task.

3. **Out of scope for this proposal**: identifying the truncating writer (no tool,
   script, or report in the repo writes a .bak — recorded as an open question in
   B5-0733 and left open here), any change to `.agent/run-queue.ps1`, any change to
   `.agent/tools/census-crosscheck.ps1`, any change to `.agent/TASK_LEDGER.md` itself,
   any change to the .bak file, and any fleet-wide protocol decision.

## Acceptance criteria (for a future implementation task, not this proposal)

- An agent that writes the ledger produces a pointer file whose hash matches the
  pre-write live file.
- A boot-time reader that has the pointer file and a matching .bak detects a truncated
  live file and falls back without silently census-ing a 1-row file.
- A boot-time reader that has a pointer but neither a matching live file nor a matching
  .bak exits non-zero with a clear message rather than reporting a false all-clear.

## Open questions

1. **Who truncates the ledger?** Neither incident has identified the actor. The .bak
   timestamp equivalence points to a single write event each time, but no known tool
   creates a .bak. Until the write path is identified, any hardening is defense-in-depth
   rather than a fix. This proposal does not answer that question; it reduces the cost
   of the next incident regardless of its cause.
2. **Pointer authority when multiple agents write the ledger.** The pointer is written
   by whichever agent last successfully wrote the ledger. If an agent writes a pointer
   then its write is later found to have introduced a defect (e.g. a pipe-count error),
   the pointer would certify a defective file. Mitigation: the pointer records the
   hash of the file as written, not a claim of correctness; correctness is still
   established by the post-write duplicate-ID census and the ledger-query pipe check,
   which are independent of the pointer. A defective file with a matching pointer is
   still defective — the pointer detects truncation, not quality.
3. **Pointer file lifecycle.** Should the pointer be git-ignored (like the .bak) or
   tracked? Argument for ignored: it is coordination state, like claims and heartbeats,
   and tracking it creates a commit-time question identical to the B5-0689 checkpoint
   question about which scratch files to exclude. Argument for tracked: a tracked
   pointer survives a working-tree wipe that destroys both the live file and the .bak.
   This proposal records the question without answering it; the honor-system adoption
   does not require a decision.

## What this proposal does not do

- It does not modify any tool, script, or ledger row.
- It does not modify `.agent/run-queue.ps1`, `.agent/tools/census-crosscheck.ps1`, or
  any file in `.agent/tools/`.
- It does not modify `.agent/TASK_LEDGER.md` or `.agent/TASK_LEDGER.md.bak`.
- It does not implement the boot-time check — that is a separate gated tool patch.
- It does not supersede B5-0733's open question about the truncating writer; it
  complementes it by reducing the cost of the next incident regardless of cause.
